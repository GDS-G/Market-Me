# Self-service account display names

Release 1.50 verified and published. This closes the narrow Settings display-name gap in specification 01–02. It does not complete the broader user-profile, identity-management or product requirements. Local full-gate, native packaging, actual browser/production acceptance, final Google readback and independent exact-source feature/main cloud verification pass and are tracked separately in [Releases](RELEASES.md); do not infer them from focused tests.

## Scope and source map

Any authenticated account may change its own application display name, regardless of workspace role. Names appear across that account's Market Me workspaces, are not unique and are never authority. Email, normalized email, provider issuer/subject, password, sessions, memberships and permissions are unchanged. The existing Settings page still requires an active workspace; the self-scoped API itself does not require a workspace membership. No administrator editor for other people's names, avatar, email change, owner transfer, deletion or provider-profile mutation is added.

- Database: `packages/database/src/account-profile-models.ts`, `account-profile-repository.ts`, their model/live tests and public `index.ts` exports.
- Schema: `0122_account_profile.sql` and forward-only `0123_account_profile_receipt_types.sql`.
- Web: `server/account-profile-api.ts`, `app/api/v1/account-profile/route.ts`, `components/account-profile-contract.ts`, `account-profile-form.tsx` and existing `app/settings/page.tsx`.
- Integration: `server/database.ts` adds the 27th shared-pool getter; `readiness.ts` requires exactly 123 migrations ending in 0123. Existing `workspace-management.module.css` supplies responsive forms/cards; the profile-only CSS module adds three-pixel keyboard focus and 44px-minimum controls/reload link without changing other forms. No new navigation entry, dependency or environment variable.
- Authentication: only the development-bootstrap conflict assignment changes in `repositories.ts`: existing names are no longer overwritten. Existing OIDC linked-identity and verified-email first-link paths already keep stored names. Session reads join the current account label.

## Models, constants and normalization

`ACCOUNT_PROFILE_LIMITS` is a frozen object: `displayName=120` UTF-16 code units and `requestBytes=4096` UTF-8 bytes. `AccountProfileError.code` is the closed invalid_input/access_denied/not_found/request_conflict/revision_conflict union. A global-registry Symbol brand supports errors across module reloads; `isAccountProfileError` requires an Error plus that brand, not an arbitrary name/code-shaped object. It is a module-identity mechanism, not a sandbox against malicious in-process code.

`AccountProfileSnapshot` contains only accountId, displayName and positive integer revision. Existing legacy names are read unchanged, even if longer than new-name limits. `AccountProfileRequest` contains only accountId, requestId, expectedRevision and displayName. `AccountProfileReceipt` adds requestId, changed and createdAt to the snapshot fields. A receipt is a historical original outcome, not current state. No email, provider identity, canonical request text or membership is returned in a receipt.

`accountProfileUuid` accepts canonical hyphenated UUIDs with version 1–8/standard variant, normalizes case and never trims. `normalizeAccountProfileRequest` requires an ordinary object and inspects property descriptors before reading values: accessors, symbols, nonenumerable fields, inherited-prototype objects, arrays and unknown keys fail. Raw names over 4096 code units or containing Unicode Cc/Cf characters or unpaired surrogates (Cs under a Unicode-aware regex) fail. Valid paired emoji remain valid scalar values. Then NFC normalization, outer trim and whitespace collapse produce a nonempty 1–120-code-unit label. Revisions are integers from 1 through 2147483647. The fixed-order accountId/requestId/expectedRevision/displayName object is frozen and its serialized UTF-8 length checked. Equivalent Unicode/spacing becomes the same canonical intent; uppercase UUIDs normalize before equality.

## Schema and atomic persistence

`app_user.profile_revision` is a positive integer defaulting to 1 for existing and new accounts. Migration does not rewrite existing names or identities. The update guard requires a changed display_name to carry exactly the next revision and a trimmed, control-free 1–120-character SQL label. Same-name updates cannot bump the revision. Maximum-revision changes fail rather than overflow. SQL character count/POSIX control rules are not claimed equivalent to the application's stricter UTF-16/NFC/Unicode format-character rules. Other account columns retain their existing lifecycle behavior.

`account_profile_receipt` columns:

| Column | Meaning and lifetime |
| --- | --- |
| account_id | Account FK, cascade only when that account is erased; combined primary key with request_id. |
| request_id | Caller-generated UUID identifying one exact intent within one account, not authorization. |
| display_name | Original normalized saved label, 1–120 SQL characters. |
| revision | Positive original saved revision, not a live revision. |
| changed | True only for a name change; false for an explicit same-name save at the correct revision. |
| canonical_request | At most 4096 UTF-8 bytes of fixed-order normalized JSON; equality controls exact replay. |
| created_at | Database clock timestamp for this original receipt. |

The canonical JSON constraint binds all four fields and disallows extra keys; expectedRevision must equal revision minus 1 for a change, or revision for a no-op. Migration 0123 adds exact JSON string comparisons for accountId, requestId and displayName. A regression reproduced PostgreSQL `->>` coercing numeric 123 to the same text as the valid label "123"; 0123 fixes the database constraint without changing the already-applied 0122 checksum. Application validation already rejected numeric names. Receipt insertion must match the account's current saved name/revision; updates and direct deletion while the account exists fail. Account-deletion cascade remains possible through existing lifecycle rules. These constraints do not turn arbitrary trusted SQL into an authenticated API.

`AccountProfileRepository.getProfile(accountId, actorUserId)` and `getReceipt(accountId, requestId, actorUserId)` call `selfScope` before any SQL. The independently authenticated actor must equal the normalized account hint. This prevents a stale form from account A renaming a subsequently signed-in account B. Missing own account/profile returns undefined on reads; saves never create accounts. Exact receipt reads join the current account. No cross-account enumeration or workspace-derived authority exists.

`save(input, actorUserId)` normalizes and canonicalizes once, then locks the actor's app_user row `FOR UPDATE` for the entire transaction. This serializes different intents, exact retries and account deletion. Look up the prior account/request key after obtaining the lock: identical canonical bytes return the original receipt with replayed=true before checking the now-current revision; different bytes produce request_conflict. For a new key, expectedRevision must equal current revision. A changed name increments once and updates updated_at; a no-op retains both revision and timestamp. At the integer maximum only a correct-revision no-op is accepted.

The same transaction writes the immutable receipt and one `audit_event` of type `account.profile_saved`, subject_type account_profile, subject_id accountId and actor_user_id accountId. Organization/workspace are null because the name is account-wide. Audit data contains requestId, previousName, previousNameTruncated, displayName, previousRevision, revision and changed. Legacy previousName is sliced to at most 120 UTF-16 units and any terminal split high surrogate removed; the explicit flag compares truncated and original text. This preserves valid JSONB Unicode even when a legacy emoji crosses the limit. No email/provider data is logged. Exact replay adds no audit or receipt. Audit failure rolls back name, revision and receipt. The audit actor FK's existing SET NULL behavior means historical audit data is not automatically erased by account deletion; no new account-erasure workflow or retention promise is introduced.

Repository `actor`, `request`, `canonical`, `current`, `prior`, `changed`, `revision`, `previousName` and `saved` are transaction/request-local values. `ReceiptRow` additionally carries internal canonicalRequest and Date|string createdAt; the receipt mapper emits only public fields and ISO time. There is no mutable global identity, authorization or result cache. The sole long-lived shared bundle contains repository handles and one lazily constructed SQL pool, not account data.

## HTTP contract

`POST /api/v1/account-profile` requires an exact allowed Origin through the existing APP_BASE_URL policy, no query, current authentication and application/json. Advertised and streamed body bytes are bounded to 4096, fatal UTF-8 decoding precedes JSON parsing, and duplicate JSON names (including escaped aliases) fail before normalization. `parseAccountProfileJson` scans JSON string tokens only after JSON.parse confirms syntax; tokens followed by a colon identify member names. The endpoint supports a flat object only; nested structures subsequently fail the strict normalizer. No provided actorUserId, role or workspaceId is accepted. Independent self-scope is checked in both route and repository.

POST returns `{data: receipt, meta: {replayed}}`, status 201 for a newly recorded outcome (including no-op) and 200 for exact replay. `GET` requires exactly one accountId and optionally exactly one requestId, with no other keys: absent requestId reads current state; present requestId looks up only that historical result. It never lists requests or writes. A missing result is 404 and explicitly does not prove an in-flight save failed.

All responses use Cache-Control private,no-store, Vary Cookie and X-Content-Type-Options nosniff, without changing cookies. Fixed error text maps origin/self-scope to 403, authentication 401, invalid input 422, media 415, bytes 413, absent result 404, key/revision conflicts 409 and unknown failures 503. Private SQL/request data is neither interpolated into public errors nor logged. `AccountProfileTransportError` is internal transport status/code; `MESSAGES` is a frozen public dictionary. CORS access is not broadened. GET URLs contain account/request IDs, not names; configure ordinary access-log retention accordingly.

## Browser state and recovery

The independent browser schema has no database runtime import. `ACCOUNT_PROFILE_BROWSER_LIMITS` is frozen: displayName120, requestBytes4096, responseBytes8192 and timeoutMs15000. `AccountProfileView` is loaded current state; `AccountProfileIntent` is readonly canonical request; `AccountProfileResult` is the original receipt. UUID, integer revision, normalized name, strict request/receipt/result schemas and optional strict replay metadata form the response allowlist. A changed receipt must be exactly expectedRevision+1; no-op exactly expectedRevision. Account ID, request ID and name must match the submitted intent. Unexpected properties, status, malformed UTF-8 and over-limit advertised/streamed response bytes fail. Names/receipts are rendered as escaped React text.

`makeAccountProfileIntent` normalizes the label, pins the loaded revision and freezes the exact request. `accountProfileLookupPath` exposes only canonical IDs. `runAccountProfileIntent` performs one POST or one explicit GET, with same-origin credentials, no-store cache, redirect:error and an AbortSignal. It checks cancellation before sending and after reading, validates response shape and never automatically retries. Error responses are mapped to bounded fixed client guidance rather than trusting arbitrary returned messages. Cancellation or timeout is not proof of database rollback.

`createAccountProfileGate` owns one form-local active `{controller,timer}` pair. `begin` rejects overlap and returns signal/current/finish closures; cancel clears the timer, aborts and invalidates the old operation. An old finish cannot clear a newer operation. This is a duplicate/late-result fence, not server authority.

`AccountProfileForm` keys its editor by accountId, not revision. `name`, `intent`, `result`, `pending` and `error` are React-local state; `retained` synchronously holds the frozen original intent before sending, blocking an immediate second submit before rerender; `mounted` prevents updates after unmount; `gate` and its active operation own abort/timeout cleanup. `profile` supplies loaded state and `router` refreshes current server labels after confirmed save/lookup. Revision-only refresh deliberately retains the original request/result; changing accounts remounts and cancels the old form. No name or request is persisted in localStorage/sessionStorage/cookies.

Once sent, editing stays locked. Check original result performs GET only, retaining the exact request after success, conflict or uncertainty. A receipt is labeled original/historical and cannot silently become current profile truth. Reload current settings obtains the latest name/revision before another intent. Leaving/reloading loses the in-memory request copy; server receipts remain subject to account lifecycle and database restore history. This explicitly does not promise recovery of an unknown request ID after reload. The form explains identity/permission boundaries, normalization, historical outcomes and that display names are not proof of identity.

Settings now distinguishes sign-in email from application label and corrects stale team copy: owners/admins already have reviewed non-owner role changes on Team. The profile lookup uses user.id for both account hint and authenticated actor; mismatched returned account data fails closed. All six roles see their own profile editor without acquiring workspace rename/create permissions.

# Workspace execution admission pause

Release 1.53 candidate: complete local/static/native/browser verification passes; cloud/publication and final documentation acceptance remain pending. The prior accepted release is1.52. [Releases](RELEASES.md) separates evidence from implementation. This is a bounded specification11/18 safety control, not a claim that the application or a hosted deployment is complete.

## Product contract

Settings → Workspace execution lets a current workspace owner or administrator review and change one durable workspace-wide admission hold. Every current member can read a minimized state. `open` means this additional hold is absent; it never means execution is approved, due, funded or otherwise permitted. A fresh review, one-line reason, separate consequence acknowledgement and expected state/grant are required for a new transition. Organization ownership alone grants no workspace authority.

The hold covers new marketing publication and retry admission, new companion claims/reclaims and new billable AI text attempts. Existing provider requests admitted before a pause may finish. Nothing recalls delivered content, cancels an external request already admitted or stops an already-open companion action. Read-only recovery, truthful completion, reconciliation and actual-cost settlement remain possible. Queue storage, drafts, campaigns, approvals, connections and history are retained. Reopening does not enable stopped AI, reactivate a worker/connection, restore membership, waive rights/approval/budget checks, revive expired windows or resume individual campaigns.

This is not a universal network disconnect. Authentication/OAuth, connection verification and webhook administration, inbound collection, analytics/report reads, local drafting, media storage and operator incident alerts are outside marketing dispatch. In particular, `OperationalAlertService` must still report safety incidents while marketing is held. Four official campaign adapters (Discord webhook, Slack webhook, Mailchimp email and Mastodon account) use the shared publication boundary. Mastodon media upload is part of an already-admitted publication operation, not a separate unguarded marketing admission. Future marketing adapters must use this same boundary before their first remote write; merely adding a button or an early state read is insufficient.

## Durable structures and normalization

`workspace_execution_control` has workspace PK/cascade, `state`, positive int `revision`, `reason`, retained `updated_by` user, `updated_by_incarnation_id`, immutable `created_at` and current `updated_at`. Backfill and AFTER INSERT workspace initialization use open/revision 1/empty reason/no actor, with both clocks equal to workspace creation time. A missing or invalid row fails closed; callers must not invent default-open state. A transition changes the state, advances exactly one revision, and requires current owner/admin identity plus matching active incarnation. The initial row cannot be directly removed while its workspace exists. Parent cascades remain supported.

`workspace_execution_control_receipt` has `(workspace_id,request_id)` primary key, unique `(workspace_id,revision)`, creator, expected actor incarnation/revision, previous/new state, reason, changed timestamp and exact `canonical_request` text. SQL validates the six JSON field types/values and no extras, bounds bytes, ties the post-revision to expected+1 and requires exact current transition evidence. Receipt updates/direct deletion are rejected while the parent exists. This is a trusted-application consistency boundary, not a sandbox against arbitrary database-owner SQL. A workspace deletion/restore can remove or predate history; receipts are not an external immutable archive.

`WORKSPACE_EXECUTION_STATES` is the frozen `open,paused` tuple. `WORKSPACE_EXECUTION_CONTROL_LIMITS` is frozen: reason 500 UTF-16 units, canonical request 4,096 UTF-8 bytes, revision ceiling 2,147,483,647. The fixed-order request contains exactly `workspaceId,requestId,expectedActorIncarnationId,expectedRevision,state,reason`. UUIDs accept the canonical hyphenated v1–8/standard-variant form and normalize lowercase without trimming. The expected revision must leave room for one increment. An ordinary-object descriptor preflight rejects missing/extra/symbol/hidden/accessor fields before reading values. Reasons reject Unicode controls, format characters and lone surrogates, NFC-normalize, trim/collapse whitespace and require 1–500 units. The canonical result is frozen. SQL character limits complement but do not replace this stricter application normalization.

`WorkspaceExecutionControlSnapshot` always contains workspace, state, revision and changedAt. Its discriminated `canManage:false` shape contains nothing else; true additionally carries the current actor incarnation and reason for a fresh review. The client flag is presentation data, not authority. `WorkspaceExecutionControlReceipt` extends the exact request with previousState, post-revision and changedAt. A receipt is historical, not a claim about present state. SQL INSERT SELECT preserves the original PostgreSQL microsecond timestamp between state and receipt; public ISO display uses milliseconds without round-tripping back into persistence.

`WorkspaceExecutionControlError` has a versioned `Symbol.for` brand checked alongside `instanceof Error`. Codes: invalid_input, access_denied, not_found, revision_conflict, request_conflict, state_conflict, execution_paused, control_unavailable. The symbol/frozen contracts are immutable module globals. Normalizer descriptors/allowed keys/raw values/reason/request are per-call locals. The expected incarnation prevents stale new changes after remove/rejoin; it never authenticates the caller.

## Transactions and lock order

Current snapshot reads take active member FOR SHARE, then control FOR SHARE; nonmembers cannot inspect tenant state. Mutation normalizes input independently, locks the authenticated current member, verifies owner/admin, serializes the exact workspace/request with a transaction advisory key from JSON `[workspace-execution-control-v1,workspaceId,requestId]`, then reads any prior receipt. Same creator and exact canonical bytes return original history without applying any state again. Fresh intent must match the active incarnation, then acquire control FOR UPDATE and match current revision and a real opposite state. State, receipt and `workspace.execution_paused`/`workspace.execution_reopened` audit commit atomically. Audit data contains request ID, previous/new state, revision, actor incarnation and reason, never credentials.

Original-receipt GET requires current administration and the original creator. A later regrant may permit historical lookup; it cannot authorize an uncommitted request reviewed under an older incarnation. Exact old reopening replay cannot undo a newer pause. Concurrent different requests reviewed at the same revision allow only one transition. Audit failure rolls everything back.

Execution admission takes control FOR SHARE before competing execution-resource locks. Read-only target/member scope validation may precede it. Publication then follows its existing instance/version/step/approval/connection/draft/asset/rights ordering; AI follows provider/intent/budget locks; companion rechecks worker identity/status FOR SHARE and performs its SKIP LOCKED claim. Pause's exclusive control lock therefore waits for an already-running admission transaction, or blocks a later admission until commit/rollback and fresh state evaluation. No provider call runs inside these transactions. Do not move a competing member/execution row lock in front of the fence without a complete deadlock review.

`lockWorkspaceExecutionAdmission(tx,workspaceId)` is the durable shared-lock boundary; `assertWorkspaceExecutionOpen(sql,workspaceId)` is only an early read to avoid unnecessary preflight/credential/fallback work. The worker uses both at their different layers. `assert_workspace_execution_admission(uuid)` additionally guards SQL publication transitions into dispatching, AI transitions into claimed, and companion claims/reclaims (including token, lease and attempt changes). MM001 means paused; MM002 means missing/inconsistent state. Completion transitions and local queued storage are intentionally not admissions. The application cannot treat a failed/ambiguous external action as safe to resend merely because the hold later clears.

Companion polling returns no job while paused, retaining queued/expired claims and worker status. Reopening never reactivates an independently paused worker. Previously claimed jobs may finish truthfully. AI claim fails before decryption/invocation, so no settlement is fabricated for unadmitted work. Already-admitted AI results can complete and settle actual cost while held.

## Workflow recovery and compatibility

`CampaignStepExecution` adds `{status:execution_held,code:execution_paused|control_unavailable,reason}`. This is distinct from `manual_required` and `schedule_blocked`. The activity layer first tries read-only exact prior-result recovery where available. If admission races a hold, it rechecks prior evidence before returning held. Accepted or ambiguous prior work wins over a new pause/expired window; it is not reclassified as an undispatched action. Unavailable legacy recovery stays held with an explicit reconciliation warning, never fabricated success.

The execution router recovers publication history and exact companion job identity (workspace/campaign/instance/version/step run/step key/idempotency key). Succeeded companion output can complete recovery; every other retained job requires review, never a replacement claim. Early hold errors happen before credentials, preflight, tracked links or fallback. The shared publication transaction remains authoritative if the hold changes during preflight. Existing adapter proof/rights/budget/approval and uncertain-outcome rules remain intact.

`execution_held` is a persisted campaign-step/domain state. It leaves `completed_at` null; its current attempt ends temporarily_failed with `WORKSPACE_EXECUTION_HELD`. A later real retry starts a new attempt. SQL permits held→held/running/waiting/canceled/schedule_blocked but rejects direct held→manual_resolution/succeeded/partially_succeeded/permanently_failed. The normal manual-completion API still requires an actual manual_resolution step. These trusted-writer guards do not prove arbitrary sequences of owner SQL are valid workflows.

Both workflow paths store held step output under `executionHold`, record context `execution.held.<stepKey>`, set the campaign paused and wait for explicit campaign Resume. Reopening workspace state alone sends no campaign resume signal. The next attempt rechecks current authorization and schedule; expired preferred windows remain schedule_blocked. Manual signals cannot mark held steps completed. Cancellation remains available.

Important workflow-local state: `holdWrites` counts in-flight hold persistence and prevents a concurrent resume signal from overtaking the paused write. `paused`, `canceled`, scheduled-path `blocked`/`failure`, revision, step-state record, copied context, approval-decision Map, requested-approval Set and manual-output Map are per workflow execution, not process globals. The legacy derivative clears any stale manual output when it enters a new hold. `holdWrites` changes command ordering only after the new held result. A resume waiting for persistence also observes cancellation. Persistence helpers finish in `finally` so an awaited hold counter cannot remain positive after settlement.

Compatibility decision: retain the existing `patched("bounded-scheduling-v1")` split; add no new patch marker. The unmarked branch now uses a compatibility derivative whose new commands occur only after the new activity result, preserving earlier paths. Frozen original 1.19 workflow/policies remain untouched. Frozen 1.52 scheduled source is a test-only fixture, not a runtime entry point. ## HTTP and browser lifetime

POST `/api/v1/workspace-execution-control` requires exact configured origin and no query, authenticated user, JSON media type, strict UTF-8 and a bounded 4,096-byte body. Duplicate/escaped duplicate keys, ambiguity and malformed input fail. Repository normalization/authorization repeats independently. New transition returns 201 and `meta.replayed:false`; exact replay returns 200/true. GET accepts exactly workspaceId alone for current state, or workspaceId+requestId for original receipt; unknown/duplicate query fields fail. An absent receipt returns 404 but does not prove an earlier request cannot still commit. No browser operation automatically re-POSTs.

All responses use fixed public errors, private/no-store, Vary Cookie and nosniff; no mutation sets cookies. Unknown persistence errors log only a constant diagnostic, not SQL/request/secret details. The common execution error mapper returns paused409 or unavailable503 with fixed text for existing execution APIs. Campaign activation/resume retain their existing validation envelope with explicit hold issue codes. The page selects its workspace server-side through current session membership; it does not accept a query-supplied actor or workspace override.

The browser contract imports no database/server/Node code. It independently validates strict snapshot/request/receipt unions, canonical reason, opposite intended state, exact original six fields, previous state, revision+1 and response envelope/status correlation. Browser constants are reason500/request4096/response16384 UTF-8 bytes/timeout15000ms/revision2147483647. All fetches use same-origin credentials, no-store and redirect:error; streamed results have fatal UTF-8 and bounded bytes. Fixed `ExecutionControlClientError` text is display-safe; arbitrary server messages are not displayed.

Panel variables: `current` is the last freshly observed state, never inferred from a receipt; `preview` is a frozen fresh review; `reason`/`confirmed` are editable only before sending. Frozen `attempt` stores userId, preview and exact request. The synchronous `retained` ref is set before POST and gates duplicate intent before React rerenders. `result` is original history; `pending` and `error` are presentation only. `gate` owns one operation/controller/timer; `current()` rejects stale/aborted completion, `finish()` clears only its own operation, and unmount cancels it. `mounted` prevents late state updates. Heading/result/trigger refs restore keyboard focus. No local/session storage, process global or background replay retains intent.

The editor key is the user/workspace/canManage/current-admin-incarnation tuple; access/scope changes discard local intent. POST clears displayed current state until a separate GET succeeds. Interrupted/unknown response keeps the exact attempt and only offers read-only original lookup; it does not assume failure or create a replacement. A confirmed receipt may coexist with unavailable current state. A fresh review is required for each next transition. Reload/navigation loses the in-panel reference while durable receipts remain; the page explicitly warns about this. Another writer's changes appear through explicit fresh reads/review, not an automatic real-time subscription. At revision exhaustion no new transition can be submitted.

## Intent and durable outcomes

One exact request means one intended campaign run, not a campaign-wide limit on repeated deliberate runs. `CampaignActivationRequest` is the fixed-order five-UUID object `{workspaceId,campaignId,requestId,expectedVersionId,expectedActorIncarnationId}`. UUIDs are untrimmed hyphenated version 1–8/standard-variant values normalized to lowercase. The database normalizer inspects own property descriptors before values and rejects nonordinary objects, accessors, hidden/symbol/extra/missing properties. Canonical JSON is frozen and bounded to 2,048 UTF-8 bytes. Expected version/grant are stale-review hints, never actor credentials.

`CampaignActivationReceipt` adds `instanceId`, immutable `initialStatus` (`scheduled` or `awaiting_approval`) and display-only ISO `acceptedAt`. It reports original acceptance, not current run progress. `CampaignActivationClosure` adds `closedAt` and means the unaccepted original request can never create a run. The discriminated `CampaignActivationOutcome` is `{kind:accepted,receipt}` or `{kind:closed,receipt}`. Closing an already accepted request returns its original receipt; it never cancels, pauses, approves, resumes or restarts that run.

The versioned Symbol.for-branded `CampaignActivationError` has fixed codes invalid_input/access_denied/not_found/request_conflict/request_closed/grant_changed/preview_unavailable. Domain constants `CAMPAIGN_ACTIVATION_LIMITS` are requestBytes 2048, previewSteps 100 and responseBytes 65536; `CAMPAIGN_ACTIVATION_INITIAL_STATUSES` is the frozen two-state tuple. No process-global actor, intent, permission, receipt cache or retry loop is introduced.

## Repository, schema and locking

`CampaignActivationRepository` is the request boundary for HTTP activation. Current owner/admin/editor is required for POST activation. Current members may read only their own original outcomes and explicitly close their exact original request; downgrade therefore does not prevent safe read/close recovery. Revocation denies access. Rejoining restores current member access to own history, but an old grant cannot authorize a fresh activation. Organization ownership alone is not workspace authority.

Lock order is current active membership FOR SHARE, request advisory lock, existing accepted/closed history, then for a fresh activation the shared workspace execution fence and established campaign/proof/route locks. The advisory key is compact `JSON.stringify(["campaign-activation-v1",workspaceId,requestId])`, hashed with hashtextextended seed 0. SQL triggers construct exactly that compact string from canonical UUID text; whitespace-bearing PostgreSQL JSON serialization is not an interchangeable lock key. Hash collisions may serialize unrelated work but cannot establish request identity.

Exact same-creator/canonical accepted replay precedes current version, grant-incarnation, pause, proof and schedule checks. It returns historical evidence without creating anything. A matching closure blocks activation; a different creator or canonical request yields conflict without disclosing history. New intent rechecks grant and all existing activation eligibility under the existing transaction. `CampaignRepository.activateCampaignInTransaction` contains the unchanged proof/approval/route/schedule/held-admission logic, inserts the exact instance/steps/start command and updates campaign status. The legacy `activateCampaign` wrapper remains trusted internal creation for existing services/tests, not an authorized/idempotent HTTP boundary; no new HTTP path may call it. Repository methods are not security against arbitrary privileged SQL callers.

Acceptance inserts receipt from the actual instance inside SQL, preserving PostgreSQL timestamp precision, and inserts minimized `campaign.activation_requested` audit in the same transaction as every activation write. `getReceipt` remains an accepted-only convenience; `getOutcome` checks accepted then closed history with creator/current-membership scope. An absent outcome is only an observation: a concurrent request can still finish. `closeRequest` serializes on the same request lock, returns an existing exact outcome or atomically creates a closure plus `campaign.activation_closed` audit. Closure does not require current published state, open execution or the old grant incarnation because it cannot launch work. It does require actual scoped campaign/version lineage and current membership.

## HTTP contracts

POST `/api/v1/campaigns/[id]/activate` accepts the complete five-field intent; the body campaign must match the route. It returns 202 with `{data:receipt,meta:{replayed:false}}` for new acceptance, or 200/true for exact replay. Old clients missing request/version/grant fields fail closed; the server never invents a request key. GET on that path accepts exactly workspaceId alone for current published review, or workspaceId plus requestId for creator-private `{data:outcome}` recovery. GET never starts or closes anything.

POST `/api/v1/campaigns/[id]/activate/close` requires the same exact five-field intent and returns 200 `{data:outcome}`. It is a separately confirmed write, not a lookup or campaign cancellation. Both writes require exact configured APP_BASE_URL origin, no query, JSON content type, bounded strict UTF-8 and no duplicate/escaped-duplicate keys. Repository normalization repeats. Session identity supplies the actor; client role/user/instance hints are rejected. Responses are private/no-store, Vary Cookie and nosniff, without Set-Cookie. Known errors use fixed text, and unexpected failures log only a constant diagnostic. Existing campaign validation maps to fixed pause/unavailable/changed-version or generic activation-not-ready responses without echoing raw SQL, exception or issue text.

`CampaignActivationPreview` is a current-member observation with workspace/campaign/version identity, published version number, campaign display name, autonomy mode, timezone, observation time and up to 100 sorted step summaries. Each summary contains stepKey/name/operationType/scheduleType/approvalRequired, not private inputs/credentials or approval proof. Only a current writer receives actorIncarnationId and canActivate true. Preview is not a lease, reservation, full eligibility test or substitute for the exact campaign definition.

## Browser contracts and UI lifetimes

`campaign-activation-contract.ts` independently validates strict browser schemas without importing SQL/Node/server authorization. Frozen `ACTIVATION_BROWSER_LIMITS` adds storedBytes 4096 and timeoutMs 15000 to matching request/response/step limits. Preview step keys must be unique. Outcomes must bind all five original request fields and the exact HTTP status/replay envelope; historical acceptance and closure are not interchangeable with live run status.

`ActivationScope` is the user/workspace/campaign tuple. `ActivationAttempt` stores schemaVersion 1, userId and frozen request only. `activationStorageKey` is `market-me:campaign-activation:v1:<user>:<workspace>:<campaign>`. Read validation checks shape, byte ceiling and every scope. Retention refuses a different existing request, writes before POST and reads back exact bytes; failure sends nothing. `forgetResolvedActivation` requires a matching confirmed outcome and unchanged original storage before removing only that exact key. No credentials, server proof or global permission is stored. Storage is tab-local, can be copied when duplicating a tab and may be cleared by the user; duplicate same-key submissions still resolve through the database boundary.

Transport uses same-origin credentials, no-store, redirect:error, one AbortSignal and bounded fatal-UTF-8 response reads. The operation gate owns one controller/timer and rejects overlapping work synchronously; identity-based finish/cancel prevents stale operations from clearing newer ones. Server messages are not displayed verbatim. Restoring state never automatically POSTs or creates a replacement. A missing GET result requires another lookup or explicit closure, not a new key. Closure uncertainty also retains the same original attempt. The panel requires a fresh review and deliberate acknowledgement after a confirmed outcome before another run.

The shared page is `/campaigns/[id]/activate?workspaceId=...&expectedVersionId=...`; the version hint is optional for direct current-version review but remains pinned when supplied by either entry point. Server authentication/current-workspace checks reject foreign or ambiguous query/path hints. The protected finalization result and advanced editor now link to this surface instead of posting directly; publication remains separate. A missing current preview does not remove recovery for a retained original request.

`CampaignActivationPanel` uses a read-only useSyncExternalStore hydration boundary; the scoped editor mounts only on the client, so storage restoration is a state initializer rather than an effect-triggered render cascade. The editor key includes user/workspace/campaign/expected-version/current-writer-incarnation. `restored` contains the initial exact tab attempt and storage availability; `storageReady` gates writes. `current` is an observed published summary, `review` is the freshly fetched frozen selection, `confirmed` and `closeConfirmed` are separate acknowledgements, `attempt`/synchronous `retained` keep one exact request, and `result` is original history. `pending`/`error` are presentation state; `gate` owns one transport operation, `mounted` excludes unmounted completions, and review/result/trigger refs restore keyboard focus. No state or ref authenticates a user.

Review cancellation creates no key. New activation persists and verifies intent before POST; lookup and closure never generate another key. A lost result leaves original controls visible and blocks replacement. A confirmed outcome remains stored until the user explicitly requests another review, a fresh scoped preview succeeds, and unchanged original storage is cleared. Stale expected versions offer an explicit current-version link instead of silent retargeting. Accepted receipts link to current run progress without claiming it is still in its original status. The timestamp is copied from transaction-time `campaign_instance.created_at`, not a measured commit instant or schedule reservation.

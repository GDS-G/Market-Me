## What the 1.25 release changes

- One owner/admin/editor configures the built-in General Announcement v1 preparation on a Smart Source. The authenticated saver becomes the configured writer; optional current Brand, ordered current Audiences, published Destination, information depth, promotional strength, timezone, name and description are validated. Source synchronization can be paused independently from the binding.
- Migration 0115 adds one mutable binding, normalized ordered audiences and an immutable-snapshot command outbox. Additive 0116 preserves a safe disable when saved reference IDs have become stale, requires complete reference validation before enablement, and orders concurrent approval/disable by commit. Only a new exact approval-pointer transition observed with an enabled binding enqueues. Existing approvals are not backfilled, same-receipt replay is deduplicated and every explicit reapproval may create a distinct command even when review bytes match.
- The ingestion worker claims one command immediately before processing, increments an attempt fence and uses the hidden command UUID as the existing preparation idempotency key. Both application and database guards reserve that UUID to the exact processing command. A crash after preparation commit replays the original receipt. Attempts 1–7 use exact 5–320-second retry delays; an expired eighth attempt reconciles an exact receipt to completed or dead-letters without a ninth claim. Deterministic stale-authority/reference/lineage failures become visible terminal state; raw exception detail is not persisted.
- Command execution rechecks the configured writer, exact current approval ID/version/fingerprint, exact configuration and current published references through the existing preparation locks. Binding edits/disabling cannot mutate or cancel queued snapshots. The Smart Source UI shows configuration and minimized recent state without command/approval/writer/lease/snapshot authority; Content Package approval warns that another explicit approval can queue another preparation.
- The result remains **Prepared—not activated**. Internal publication of an immutable `draft_only` planning version is required for generation lineage and is not external publication. No finalization, Draft/Campaign approval, Campaign instance, workflow command, activation, schedule, publication action, credential/provider access or send is added.
- Release readiness expects migration 0116/count 116. The frozen migration replay/checksum gate, live source-preparation database suite, web/full workspace tests, all typechecks, lint, frontend builds, authenticated browser acceptance, production smoke, Windows native/package gate, Google development-document synchronization, exact reviewed feature/main Linux runs with both clean audits and publication on `main` are verified. Local audits remain unverified because registry disclosure was blocked.

## What the 1.24 release candidate changes

- One raw, bounded PostgreSQL capture preserves package, evidence, conflict, asset, extraction, scan, accessibility and rights state with six-digit UTC, decimal bigint, JSON key fidelity and lossless numeric checks. Strict canonical bytes and a domain-separated fingerprint add the material-change identity that numeric package versions lack; lossy or partial capture cannot be approved.
- Effective evidence is derived deterministically from complete supersession/conflict state. Duplicate IDs, invalid graphs, open/dismissed/inconsistent conflicts, unresolved active claims, missing facts and current asset blockers fail closed with no partially trusted evidence subset.
- Explicit material actions require the displayed numeric version and review fingerprint. Every accepted change clears the current approval and returns the package to review/ready rather than silently preserving `approved`; prior receipts, decisions and generated-work provenance remain immutable history.
- Approval stores an idempotent exact receipt, Learning Review decision proof, current pointer and minimized audit atomically. General audit omits raw claims, alt text/notes and private rights narrative/scopes; the access-controlled approval receipt and decision proof hold their respective accountable detail. Direct history deletion is refused while the workspace survives, with only whole-workspace/organization erasure allowed.
- Draft generation, General Announcement preparation and new finalization require the current exact receipt and approved effective-evidence set. Finalization retains its original generation receipt and allows a newer receipt only for byte-identical content. These gates add no Draft/Campaign approval, publishing, activation, provider call or rights waiver.
- Migration 0113 is the frozen stop-the-world, forward-only writer boundary. Additive function-only migration 0114 closes direct Learning Review evidence detachment while preserving the existing foreign-key source-refresh path. Old writers intentionally fail after 0113; matching readers/writers/UI and both migrations must deploy together. The triggers/admission marker assume a trusted least-privilege database role and are not a defense against arbitrary same-role or administrative SQL. The final local gate, Google documentation readback, exact feature/main Linux CI and reviewed-source publication on `main` are verified.

## What the 1.20 preview changes

- **Time comes from durable evidence.** Version-pinned UTC windows are inclusive at the start and exclusive at the end. Dependency delays use each same-instance predecessor's first durable success/partial success, never an activity retry time. PostgreSQL supplies fresh time after authorization locks; conservative monotonic request budgets prevent a slow or backwards worker clock from extending a deadline.
- **Expiry is distinct from uncertain delivery.** Undispatched expired work becomes `schedule_blocked` and pauses the instance. Resume and all manual completion are rejected; cancel and a newly reviewed plan are the initial recovery. Started writes settle or reconcile. Exact persisted successes replay without credentials, links, media or provider calls.
- **Branches and approval waits remain recoverable.** The Temporal `bounded-scheduling-v1` patch retains frozen 1.19 behavior for unmarked histories. Independent eligible branches progress without unrelated slow siblings. Three real history replays cover new and legacy paths. Deploy the new worker before enabling new web activation; retain the legacy path while histories remain in retention.
- **Publication admission is shared.** Initial claims and failed retries recheck exact identity, current approvals/content/account state and schedule under one lock boundary. One winner may send. Late preflight health writes cannot reactivate a revoked connection or overwrite a changed credential/configuration snapshot. This is not an atomic guarantee across every rights writer and external HTTP.
- **Authoring and controls expose the actual scope.** Delay values, UTC milliseconds, optionality and advanced objects survive edits. Calendar shows authored bounds and pinned evidence without inventing a reserved slot. Windows require a current publish-capable official API connection and supported text-only route; companion mixed plans, recurrence and pacing remain separate work.

See [Scheduling contracts](SCHEDULING_CONTRACTS.md) for types, maps, locks, error/recovery semantics and clock assumptions.

## Historical 1.19 preview changes

- **Current workspace is consistent.** `getActiveWorkspace` and the shared shell check membership on every request. The cookie is a hint; switching is origin-checked and membership-authorized, and only safe section roots survive navigation. Revoked or absent membership cannot reveal another tenant's records. A zero-membership account receives a stable no-access screen. Settings shows actual facts and existing Team invitation controls without fictitious save buttons.
- **Overview/calendar show persisted evidence.** Overview summarizes saved records and pending queues, not demo results or live health. Calendar reads immutable version snapshots for runs, clearly labels draft/published plans that are not queued, distinguishes fixed-time and untimed work, and reports unsupported execution semantics. It does not claim recurrence, collision prevention, scheduling optimization, or guaranteed delivery.
- **Campaign plans survive ordinary editing.** Explicit UTC fields preserve absolute instants, seconds/milliseconds, window bounds and advanced condition/input/output objects. Execution methods, optionality, retries and timeout values round-trip. Publishing/activation semantics distinguish draft from currently published versions. Unsupported fields remain editable but cannot silently become immediate actions.
- **Approval and execution authority are real checks.** Draft-only/unknown modes cannot run. Whole-campaign approval captures the exact version/steps; `__campaign__` is reserved. Queued activities check active/running state, due time, finished dependencies and current approvals; publication creation rechecks exact lineage and target-bound idempotency. Confidence/history modes retain review until their actual waiver logic exists, and stricter provider approval rules still apply.
- **Failed publication retries have one owner.** The retry comparison-and-set grants permission to one caller only. Original rendered content/subject, complete provider identity, exact approved preview and current authority are checked; losers do not send or overwrite active state. This is not a transactionally locked guarantee over all mutable media-rights reads and provider I/O; that common dispatch boundary remains production hardening.
- **Collector backlog has retained incidents and claim fencing.** Migration 0108 adds one active overdue/abandoned incident per workspace/type, five-minute thresholds, collection-equivalent eligibility, one observer snapshot and advisory locking. Automatic snapshot/completion writes carry the claim's attempt number. Recovered claims cannot be overwritten by old workers. Monitoring remains coupled to the enabled collector and does not independently detect a stopped process or deliver a pager notification.

## Bounded next roadmap

1. **Complete the beginner content-to-campaign workflow.** Extend the delivered Smart Source-to-General-Announcement exact-approval binding with reviewed reusable templates, a preview of generated steps/drafts/destinations, optional ready-before-approval planning where product policy permits, and guarded handoff through final review/launch. Acceptance: a nontechnical operator can configure a folder and context, correct its interpretation, approve a draft, and launch the intended Campaign without editing JSON or losing/repeating work after restart.
2. **Extend scheduling beyond the bounded text-only scope.** Add recurrence/evergreen/follow-up and supported conditions with timezone/DST behavior, blackout/quiet-hours policy, collision reporting and durable per-action pacing. Extend deadlines to multistage media and companion only with end-to-end enforcement. Acceptance: representative time changes, dependencies, parallel branches, stops and worker restarts preserve the intended schedule and never dispatch early or duplicate completed actions.
3. **Complete one real provider inbox-to-reviewed-response flow, then expand.** Ingest authorized provider messages with stable identifiers and reconciliation, preserve relationship/context/suppression, send an explicitly reviewed response, record the provider result and handle ambiguity. Extend to bounded live discovery/outreach only with configured contact authority and pacing. Acceptance: continuity, handoff and do-not-contact behavior hold across incoming/reply/follow-up cycles.
4. **Connect useful AI and media processing to the main workflow.** Turn current model/budget controls into simple task choices with evaluated grounded outputs; support local/self-hosted execution and the required audio/video/accessibility jobs. Preserve source evidence and cost/privacy constraints. Acceptance: representative evaluation sets and actual provider/local runs prove quality, billing reconciliation, privacy location and failure behavior before promotion.
5. **Deliver measurable outcomes and operational completeness.** Add analytics views, lead/commerce events, experiment allocation/results and reviewed optimization. Finish independent monitoring, whole-system restore and load drills, retention/export and administrator controls. Acceptance: campaigns can be traced to source, approval, execution, cost and outcome through interruption/recovery without invented metrics or missing evidence.
6. **Validate supported platforms and distribute intentionally.** Produce signed/updateable companion artifacts and deployment instructions for Windows, macOS, Ubuntu and CentOS Stream/RHEL-compatible environments; exercise Docker/Podman and Chrome/Edge/Firefox/Safari as specified. Public reviewed-source publication is already authorized. Acceptance is installation, login, update, browser/local-folder job and health/recovery on each required target, not merely shared source compiling on Windows.

# Workspace creation, naming and exact request recovery

Release 1.32 implementation reference. Local full regression/build/native-package, production and synthetic browser acceptance pass. Exact-source cloud verification and final Google documentation readback remain in progress. See [release evidence](RELEASES.md) for final acceptance, and [scope plan](WORKSPACE_MANAGEMENT_PLAN.md) for the original boundaries. This feature does not complete organization administration or the full product specification.

## Ownership and scope

An existing organization owner may create an empty sibling workspace. A current workspace owner or administrator may rename that workspace. These permissions are independent: organization ownership does not grant access to an existing workspace, and workspace administration does not grant organization-wide creation authority. Settings reads require current workspace membership; the creation page separately checks current ownership of the explicit organization. Repository transactions recheck authority even after successful page rendering.

Creation inserts a server-generated workspace UUID, immutable `workspace-<UUID>` slug, UTC default timezone, the creator's sole workspace-owner membership and one ordinary default Brand named after the initial workspace. It does not publish a Brand Profile or inherit anyone else's membership, profile, content, connection, credential, preset, source, Campaign, AI override or execution record. It creates neither an organization nor an external account. Existing OIDC identity linkage, bootstrap allowlist, invitation policy and production sign-in restrictions remain unchanged.

Rename updates only `workspace.name`, `settings_revision` and `updated_at`. Organization, ID, slug, creation time, timezone, Brand/Profile names, membership, content and Campaign history are unchanged. Display names need not be unique: identity and exact recovery depend on UUIDs, never a label. Existing names may predate the new validation rules; do not rewrite them during migration.

## Source map and data contracts

- `packages/database/src/workspace-management-models.ts`: public input/result types, limits, canonical normalization and branded domain errors. `WORKSPACE_MANAGEMENT_LIMITS` is frozen at 120 UTF-16 code units for new names and 4,096 UTF-8 bytes for canonical requests. `ERROR_BRAND` uses a global symbol so safe errors still map correctly across module copies/prototype changes; do not treat an arbitrary error's `name` or `code` as trusted.
- `workspace-management-repository.ts`: authority reads, serialized transactional mutations and actor-private receipt recovery. Its sole instance field `sql` is the shared database client, not cached authority. `AuthorityScope` is the create-organization or rename-workspace union; `ReceiptRow` contains private persistence fields. The `receipt()` mapper deliberately removes `createdBy` and `canonicalRequest` and converts the timestamp to ISO text.
- `apps/web/src/server/database.ts`: `workspaceManagement` joins the factory's repository bundle. Development stores it in `globalThis.marketMeDatabase` to avoid hot-reload connection churn; production does not retain it in that global cache. Restart the development server after changing repository constructors/prototypes. Authentication and membership are read per operation, never cached in the bundle.
- `apps/web/src/server/workspace-management-api.ts` and `app/api/v1/workspace-management/route.ts`: bounded JSON transport, exact-origin mutation and private no-store recovery. `WorkspaceManagementTransportError` carries safe transport code/status/message, separate from database errors.
- `components/workspace-management-contract.ts`: browser-only Zod schemas, name normalization, exact saved attempts, stream reader and network runner. It does not import the database runtime or trust browser authority. `WORKSPACE_BROWSER_LIMITS` duplicates the 120/4,096 name/request bounds and additionally caps recovery/response documents at 8,192 UTF-8 bytes. Changing the protocol requires updating both validators, tests and documentation.
- `components/workspace-management-form.tsx` and its CSS module: browser-gated create/rename form, retained-request recovery, current settings reload and explicit switching instructions. `WorkspaceManagementBoundary` is a pure explanatory renderer. `app/settings/page.tsx` and `app/settings/workspaces/new/page.tsx` obtain authoritative props and show only permitted controls.

The closed create request is `{operation:"create", organizationId, requestId, name}`. The closed rename request is `{operation:"rename", workspaceId, requestId, expectedRevision, name}`. IDs are UUID versions 1–8 with an RFC variant; server input trims/lowercases them. Revision is an integer from 1 through 2,147,483,647. Name normalization rejects C0 controls and DEL before applying Unicode NFC, trimming and whitespace collapsing. It rejects empty/overlong results. The ordinary-object validator inspects property descriptors before reading fields, rejecting inherited prototypes, hidden/symbol fields, accessors and unrecognized properties. The invocation-local `allowed` Set is the operation-specific field allowlist. The normalized frozen object has deterministic property order for exact canonical JSON comparison.

`ManagedWorkspaceSettings` contains `workspaceId`, `organizationId`, `organizationName`, `name`, `revision`, `canRename` and `canCreateWorkspace`. The two Boolean capabilities are independently derived from current database roles. `WorkspaceManagementReceipt` contains only `organizationId`, `workspaceId`, `requestId`, `operation`, original normalized `name`, resulting `revision` and `createdAt`. A receipt is an immutable original outcome, not proof of today's name or access.

## Schema, locks and atomicity

Apply additive `0119_workspace_management.sql` before deploying the matching web/database code. Readiness requires exactly 119 migrations ending at that filename. The frozen SHA-256 is `55e44aa09b5c34e33c81e5134562829542e8fc3520d78fae31f74c6b60ec5372`; do not edit applied SQL. Earlier migration checksums remain unchanged.

`workspace.settings_revision` is a positive integer defaulting to 1. A composite unique constraint on `(id, organization_id)` supports receipt tenant integrity. The update trigger forbids changing workspace ID, organization, slug or creation time. A changed name requires the next revision and a bounded, trimmed, control-free label; an unchanged name cannot advance revision. The repository additionally enforces its stricter Unicode/canonical and no-op rules and rejects revision exhaustion before arithmetic overflow. No new workspace-name uniqueness constraint is added.

`workspace_management_receipt` has primary key `(organization_id, request_id)`, composite workspace/organization foreign key, actor foreign key with delete restriction, operation, name, revision, canonical request text and server creation time. An index supports workspace/time access. Checks require a bounded JSON object with the exact closed operation fields, matching scope/request/name and a correct create revision or rename predecessor revision. The insert trigger requires matching current workspace name/revision and the actor's appropriate authority; create additionally requires creator workspace ownership. Updates and individual deletion while the parent remains are rejected. Whole-workspace/organization cascading erasure removes receipts; this feature provides no deletion UI.

Transactions run in this order:

1. Normalize input and actor; derive the current organization using operation-specific authority. Create locks organization and owner membership `FOR SHARE`; rename locks the qualifying workspace membership `FOR SHARE`. Role revocation either wins first and denies the operation, or waits until the admitted transaction completes.
2. Acquire transaction advisory lock for `workspace-management:<organizationId>:<requestId>` using `hashtextextended`. A hash collision only serializes unrelated work; the table's exact key and canonical comparison still decide identity.
3. Read a prior receipt. Exact actor and canonical request match returns the original result without applying anything again; changed input or another actor receives `request_conflict`. Authority is checked before replay. Replay precedes current name/revision checks so later legitimate renames do not invalidate earlier completed requests.
4. Create the empty workspace/default Brand/creator membership, or lock the current workspace row `FOR UPDATE`, compare `expectedRevision`, reject unchanged name and write the next revision.
5. Insert the immutable receipt and one `workspace.created` or `workspace.renamed` audit event in the same transaction. Audit JSON contains normalized new `name`, resulting `revision`, and for rename the preexisting `previousName`. That historical name is preserved verbatim and can exceed today's new-name bounds; it is not copied to the browser receipt. Failures roll back the entire mutation.

Lookup uses a transaction with the same operation-specific current authority and requires original actor, exact organization/request key and operation; rename additionally matches workspace. It does not acquire the mutation's advisory lock or wait for an uncommitted result. Therefore 404 means “not visible yet,” not proof that an earlier request failed. Another actor cannot enumerate a receipt simply by knowing its request UUID.

## HTTP and selection behavior

`POST /api/v1/workspace-management` requires the exact configured `APP_BASE_URL` origin, no URL query, authenticated user, JSON content type and both advertised and streamed 4,096-byte bounds. The reader's invocation-local `chunks` array, `length`, `bytes` and `offset` implement a bounded UTF-8 decode; oversized streams are cancelled and reader locks released. Invalid JSON/UTF-8 returns 422, unsupported media 415 and oversize 413. The repository alone decides operation authority. New completion returns 201, replay 200, with `{data:receipt,meta:{replayed}}`. No active-workspace cookie is set by this route.

`GET` on that endpoint accepts exactly `operation`, `requestId` and one `organizationId` for create or `workspaceId` for rename. Duplicate, missing or unknown parameters are rejected; authenticated actor comes only from the session. Result is `{data:receipt}` or an honest 404. Both routes use `Cache-Control: no-store`. Authentication maps to 401, current permission denial 403, invalid input 422, unavailable target 404 and request/revision conflicts 409. Unknown persistence errors produce a fixed 503 warning; private SQL/request fields are not returned or logged.

`MarketMeRepository.listWorkspaceAccess` now orders by membership creation time, then workspace creation time and immutable ID, not mutable name. This fixes the observed no-cookie first-run bug where adding an alphabetically earlier workspace switched the default on reload. `selectActiveWorkspace` still honors a current membership from `mm_active_workspace` first and never treats the cookie as authority. Existing users with no valid preference may see their oldest permitted membership become the fallback once at deployment; valid saved choices remain unchanged. Sidebar ordering follows this stable membership order. No timestamp-based list order can preserve access that was actually revoked.

After successful creation the user deliberately reloads settings/choices, selects the resulting workspace and chooses Switch workspace through the existing membership-checked action. The form never automatically navigates into another tenant or alters selection. The current renderer and sidebar may show their loaded pre-mutation names until refreshed; the result receipt is labeled as the original outcome.

## Browser recovery state, collections and lifetimes

`WorkspaceScope` is user + organization + operation, with workspace ID for rename. `workspaceStorageKey()` forms `market-me:workspace-management:v1:<userId>:<organizationId>:<operation>:<new-or-workspaceId>`. The versioned `WorkspaceAttempt` stores `{version:1,userId,organizationId,request}` in `sessionStorage`, not credentials or role claims. Create and rename, different organizations/workspaces and different signed-in users have separate keys. The request and receipt schemas are strict; unknown authority fields are not stripped and silently accepted.

`makeWorkspaceAttempt` checks exact scope and canonical name. `restoreWorkspaceAttempt` bounds serialized bytes before parsing and rejects incompatible versions/scopes. `persistWorkspaceAttempt` compares any existing normalized attempt, refuses to replace a different request, stores exact JSON and reads it back. Storage failure prevents that action's network request. The UI persists and freezes first; `runWorkspaceAttempt` rechecks persistence before fetch. Both initial submission and retry therefore use the same immutable request UUID/body. The browser does not generate a replacement key after an uncertain outcome.

`runWorkspaceAttempt` chooses explicit POST or read-only GET, disables fetch caching, bounds response content type/bytes and validates its envelope. `parseWorkspaceReceipt` requires matching organization, request, operation, normalized name and resulting revision (create 1; rename predecessor + 1), plus exact workspace for rename. UUIDs and ISO timestamps are validated before rendering. A malformed, wrong-scope, oversized, failed or dropped response leaves the local attempt retained. Even a parsed 404/409 does not automatically unlock new edits. The response reader owns a bounded `chunks` array and decoding counters until it releases the stream lock.

The hydration gate uses `useSyncExternalStore` with constant browser/server snapshots so no form is enabled before recovery storage has been inspected. `WorkspaceEditor` remounts on scope or loaded revision change. Lazy `restored` holds initial raw serialization, parsed attempt and read error. `attempt` freezes the exact request; `name` holds unsent input or the restored normalized label; `storageError` blocks unsafe sends; `pending` controls feedback; `error` holds bounded safe failure text; `result` is only a validated original receipt; `confirmed` is explicit discard acknowledgement. The `inFlight` ref blocks duplicate dispatch/reset synchronously, `mounted` suppresses late state updates after unmount, and `retained` tracks the exact local serialization so clearing does not remove a different request written since load.

Clear requires explicit acknowledgement, no in-flight request and a storage comparison, removes only the current scoped local key, verifies removal and performs a full page reload to obtain current revision/authority. Malformed initial recovery can be explicitly cleared only with the same warning/acknowledgement. It never deletes the server receipt or rolls back a completed operation. Closing a tab may lose its local request copy; parent erasure or a database restore before the operation can remove server recovery. Do not promise recovery beyond those boundaries.

## Acceptance and operation

Focused tests currently pass 47 database tests and 68 web tests. They cover canonical descriptors/Unicode/limits, independent role combinations, cross-organization denials, actual scoped data reads, zero inherited records, six concurrent creates, competing renames, unchanged/stale rejection, immutable receipts, cascade erasure, actor-private replay, revoked authority, both real lock-order races, stable no-cookie ordering, closed API transport, strict response matching, storage failure, byte-identical network retry and server-rendered role controls. The integration suite accepts only isolated `market_me_ci` or `market_me_qa_132_*`, not the application database.

Synthetic browser acceptance used `market_me_qa_132_workspace_v1`. One empty sibling workspace and two successful display-name edits produced three receipts; exact replay added no duplicate. A second tab's stale revision was rejected, its missing receipt remained ambiguous, and explicit acknowledgement/reload recovered current settings. New-workspace switching showed an empty source list and separate editable recovery scope. A 430-pixel viewport measured 415 content/client pixels, with no horizontal overflow; final captured tab error log was empty. No provider connection, Campaign, content publication or production permission changed. The default-selection bug found by this check was fixed and retested after restarting the development repository cache.

For rollout, back up, drain workspace mutations, apply 0119 once, restart matching web/database code and check schema readiness. No dependency, secret, environment variable, worker, provider scope or credential change is required. Do not remove receipts or decrement revisions to retry an operation. To recover an uncertain UI result, check/retry the exact retained request; if current authority was revoked, restore access only through separately authorized administration, not a recovery bypass. Organization creation/renaming, member-role editing/owner transfer, deletion, billing, public signup and workspace cloning remain outside this release.

# Exact AI-policy save recovery

Release 1.41 implements the [bounded plan](AI_POLICY_SAVE_RECOVERY_PLAN.md). Acceptance and publication are tracked separately in [Releases](RELEASES.md). This is policy-save concurrency and response recovery, not provider execution, spend approval, currency reinterpretation or whole-product completion.

## Problem and transaction boundary

The previous form could leave pending true on a network rejection, refresh after malformed successful JSON, and send duplicate same-tick mutations. Three pre-fix handler tests reproduced those failures. The old PUT had no loaded-revision precondition; a late response or stale editor could silently replace newer settings. The trusted repository writer also reread after commit and could return a different writer's result.

Each new save binds the complete normalized settings, workspace, original actor, UUID requestId and expectedRevision. Within one transaction the repository locks current authoring membership, acquires a request-specific advisory lock, looks for an original receipt, checks/locks current revision, writes the policy, inserts the immutable receipt and writes one existing ai.policy_saved audit. A failed step rolls back all three effects. Same-key replay returns the original receipt before checking the current policy revision but only after checking current authority and exact canonical request/actor equality. It never reapplies the original policy or creates another audit.

For a first save, expectedRevision is zero and absence is required. The conditional ON CONFLICT update separately rejects an insert that loses to an uncommitted first writer; SELECT FOR UPDATE cannot lock a nonexistent row. Existing saves require exact revision equality. No-op writes still advance revisions, preventing a stale edit from passing after intervening changes. At 2,147,483,647 further saves fail closed. A different-key concurrent writer gets a revision conflict; same-key concurrent retries get one first result and one replay.

Current owners/admins/editors may save. Recovery additionally requires the original actor. The membership FOR SHARE lock holds authority through commit and makes a simultaneous demotion wait; a demotion committed first denies the operation. Recovery by another current writer yields no receipt. No public receipt listing or actor override is exposed. Receipt lookup is read-only and may see no row while a save is still uncommitted; absence is not proof of failure or cancellation.

## Server inputs, values and storage

`packages/database/src/ai-policy-save-models.ts` defines:

- `AI_POLICY_SAVE_LIMITS`: frozen requestBytes=4096 and maxRevision=2147483647. No mutable global cache is introduced.
- `AiPolicySaveRequest`: workspaceId, requestId, expectedRevision and all WorkspaceAiPolicyWrite fields. UUIDs are trimmed/lowercased, then checked for versions 1–8 and RFC variant. expectedRevision is an integer 0..maxRevision; zero denotes unsaved policy, not revision one.
- Policy fields: mode, maximumPrivacyClass, failoverMode and capBehavior use the existing closed domain arrays AI_MODES, AI_PRIVACY_CLASSES, AI_FAILOVER_MODES and AI_CAP_BEHAVIORS. currency is three uppercase letters. Optional dailyBudgetMinor/campaignBudgetMinor/monthlyBudgetMinor, when present, are integers 1..1000000000. Missing means no cap; explicit null/undefined/zero is rejected by the new server contract. No amount conversion occurs in persistence.
- `alertThresholdPercentages`: a copied/frozen array of one to five unique ascending integer percentages 1..100. Extra, hidden, accessor, sparse and subclassed array input is rejected. Caller arrays are not mutated.
- `normalizeAiPolicySaveRequest`: checks a plain JSON-like object, own enumerable data properties and closed fields without invoking accessors; rejects caller-supplied execution/actor fields; constructs fixed canonical field order and freezes the result. `aiPolicySaveUuid` normalizes scope identities; `aiPolicySaveValues` removes requestId/expectedRevision and returns the policy subset.
- `AiPolicySaveError`: closed invalid_input/access_denied/request_conflict/revision_conflict/not_found codes and a Symbol.for brand checked by isAiPolicySaveError. Branding survives bundled class-identity differences without treating an ordinary matching name/code object as trusted. Messages are safe operator explanations, not SQL or provider text.
- `RevisionedWorkspaceAiPolicy`: existing stored policy plus revision. getPolicy returns values and revision from one row/snapshot. Existing global StoredWorkspaceAiPolicy types and internal budget calculations are unchanged.
- `AiPolicySaveReceipt`: workspaceId, requestId, committed revision, original policy and ISO createdAt. It is historical evidence only, not current policy, membership, provider readiness, a cost quote or execution authority. The row mapper revalidates the stored policy subset and never substitutes a current-policy read.

Migration `0121_ai_policy_save_recovery.sql` adds workspace_ai_policy.revision with default one. Existing currency tags, amounts, optional nulls, metadata and timestamps are untouched. The trigger advance_workspace_ai_policy_revision requires initial revision one, automatically increments every update, protects workspace/creator/creation identity, blocks direct revision reassignment and blocks deletion/reset while the workspace exists. Workspace/organization erasure retains the existing cascade semantics.

`workspace_ai_policy_save_receipt` is keyed by (workspace_id,request_id). created_by references the original app_user with RESTRICT; revision is positive; policy_snapshot is JSONB; canonical_request is at most 4096 UTF-8 bytes; created_at is the database clock. Checks bind JSON scope/key, expectedRevision=revision-1 and the stripped canonical policy to the snapshot. protect_workspace_ai_policy_save_receipt validates the actual policy revision/snapshot/updated_by and current writer role at insertion; updates and direct deletes are forbidden. Only workspace erasure permits cascade deletion. The actor/time index supports workspace-private recovery. These are consistency defenses, not protection against a database administrator disabling triggers.

`AiRepository.savePolicyExactly` is the guarded browser boundary. `getPolicySaveReceipt` returns only the original actor's receipt under current writer authorization. `lockPolicySaveWriter` locks the membership row. `writePolicy` is shared with the trusted legacy savePolicy method and returns that statement's actual RETURNING snapshot inside the transaction, eliminating the post-commit reread race. Legacy savePolicy remains an internal unconditional writer with existing validation/authorization; its writes advance the database revision but create no exact-request receipt. It is not reachable through an unguarded browser PUT. Advisory lock input is ai-policy-save:<workspace>:<request>, hashed with PostgreSQL hashtextextended; collisions can serialize unrelated work but cannot widen scope or replace exact equality checks.

## HTTP and browser contracts

POST /api/v1/ai-policy/saves and the former PUT /api/v1/ai-policy share saveAiPolicyRequest. Both require the configured same Origin, authentication, no query authority, application/json, at most 4096 advertised/streamed bytes and valid UTF-8 JSON. The repository independently repeats validation/authorization. First success is 201 with data receipt and meta.replayed=false; replay is 200/true. Responses are no-store. GET /api/v1/ai-policy/saves accepts exactly one workspaceId and requestId, requires current actor authority, returns 200/data or 404 with explicit in-flight uncertainty. Duplicate/unknown query fields fail closed.

Safe mappings: 401 authentication; 403 origin/access; 404 missing; 409 request/revision conflict; 413 size; 415 media type; 422 input. Unknown failures produce a constant 503 uncertainty response and constant minimized log line, never private request/SQL details. The older GET /api/v1/ai-policy remains the existing current-policy/usage view. Old browser clients lacking requestId/expectedRevision now fail validation instead of retaining a lost-update bypass.

`ai-policy-save-contract.ts` is a browser-only Zod contract; it imports no database runtime. Types PolicySaveRequest/Attempt/Receipt/Scope describe a version-1 envelope {version,userId,request}, response and account/workspace scope. AI_POLICY_BROWSER_LIMITS is frozen: request4096, recovery8192, response8192 bytes, timeout20000 milliseconds. UUIDs are already canonical in this browser contract. make/restore/checkScope clone, validate and freeze attempts/arrays. The storage key is market-me:ai-policy-save:v1:<userId>:<workspaceId>; its version is independent of app release 1.41.0.

policySaveRequestFromValues keeps the established hundredths display convention: parse up to two decimal places without floating-point rounding, retain blank optional caps as absent, and reject invalid nonempty caps rather than removing them. Alerts are not silently filtered, sorted or deduplicated. Currency display normalization is trim/uppercase only. Existing non-two-decimal-currency semantics remain a separate audit: this release does not silently reinterpret historical money. aiPolicyValues continues to convert stored fields into the nine existing editor values.

persistPolicySaveAttempt refuses a different retained attempt, writes and verifies exact bytes synchronously before network I/O. runPolicySaveAttempt revalidates/persists, sends either explicit GET lookup or one POST, uses no-store and a 20-second AbortSignal, bounds streamed response bytes, rejects invalid UTF-8/JSON and requires the exact envelope/status/replay combination. parsePolicySaveReceipt checks every original policy field, scope, request and expectedRevision+1. Error-code explanations come from a frozen own-key dictionary; arbitrary server strings are not displayed. There is no automatic retry, save, lookup, clear or refresh. Aborting a response does not cancel/roll back a server commit.

## React state and operator recovery

AiPolicyForm uses useSyncExternalStore for a stable static preview and hydration gate. Before hydration, saving is disabled and browser storage is not read. AiPolicyPanel is keyed by account, workspace, permission, loaded revision and hydration state; the server page additionally keys the full saved policy and role. The page supplies userId and revision from the same authenticated policy read. A retained attempt initializes the controls with its own values, not newer current settings, and labels them as retained-request settings. The page's loaded revision and the retained request's original precondition remain separately visible.

useAiPolicySaveRecovery owns per-mounted-form state: restored (original raw bytes/parsed attempt/error), values, attempt, storageError, pending, error, result and confirmed. inFlight is a synchronous ref fence against same-tick handlers; exactRequest holds the original attempt even before rerender; retained holds verified raw storage bytes; mounted prevents async completion from setting unmounted state. The mounted effect performs no network work. frozen disables mode cards and every policy field when not hydrated, unauthorized, pending, retained or storage-unreadable. run always releases pending in finally. Other budget-alert/exception actions keep their independent state and are outside this release's recovery scope.

After any result—including success, 404, conflict, malformed response or connection loss—the exact attempt stays retained and editing stays locked. Check saved policy result is read-only; Retry same policy request reuses identical fields and key. A verified result says Confirmed original policy save and explicitly does not claim current settings. Reload current policy and costs reloads the page without discarding the local recovery key. A complete reload alone does not automatically fetch a receipt or imply success.

Clearing requires the explicit acknowledgement checkbox, no in-flight request, matching current raw storage bytes and a verified removal. An initial failed storage read never authorizes deleting an unknown later-visible request. Clearing reloads the document to obtain fresh revision/authority; it does not reset in place with stale props or cancel earlier work. This control removes only the tab-local copy, not the server receipt. The browser QA intentionally retains its recovery copy; clearing/race guards are tested with isolated in-memory storage.

Recovery settings are not credentials, but sessionStorage is not an encrypted vault. Same-origin script access and the browser's existing security boundary apply. Local copies can be lost by closing tabs, account/browser cleanup or storage failure. The server has no receipt directory; recovery needs the original key and current original-actor access. Retention also ends with workspace erasure or a restore that predates the request. A historical receipt must never be treated as a permission or current-state token.

## Verification, rollout and limits

Coverage includes the three reproduced handler failures, malformed/oversized transport, exact response matching, blocked/changed storage, account/workspace separation, retained replay across reload, clear acknowledgement/stale-copy protection, current-role denial, request-key conflicts, no-op revisions, receipt immutability and original legacy-writer results. Database race tests prove contenders actually reach a PostgreSQL lock before releasing commit/rollback and role-demotion barriers; they do not rely on timing-only Promise.all races. Live fixtures are limited to market_me_ci or market_me_qa_141_* and clean only exact test organizations/users.

The one-time CI upgrade proof creates three synthetic historical currency-tag policies at schema120, applies only0121, verifies every field unchanged except revision=1, proves no invented receipts and replays all121 checksums. Migration SHA-256: d53b27d21c4009cc80f5dCDD6A32C8BCFFF280C682263EEB132743B7E1D43027 (case-insensitive hex). The runtime readiness constants require exactly121 migrations ending at0121. The first broad gate caught the obsolete120 expectation; its corrected successor must pass before release.

Ignored QA helpers qa-ai-policy-141.ts and verify-ai-policy-141.ts target only loopback market_me_qa_141_policy_v1. Seed once, never replay it; --status is read-only. Browser QA saves one lower-cost preference without changing caps/security, restores/checks/retries that exact key after one explicit synthetic later-writer change to faster, and preserves all141 measured domain-table fingerprints on replay. Exactly138 tables stay unchanged throughout the saves; only policy, one receipt and two incremental audits change. No provider credentials, execution windows, reservations, quotes, invocations, campaigns or publications are created. Mobile390x844 has375-pixel content/client width and no overflow; viewport is reset. Scope does not include actual provider execution or production deployment.

Deploy migration0121 before the new web build. Keep the migration and receipts immutable. To roll back the application, stop policy mutations first; old web code does not enforce the new request protocol and must not remain an unguarded write path. Retain the additive schema/history; use a successor migration for later schema changes. No dependency or new environment-variable configuration is required. Continue using current DATABASE_URL/APP_BASE_URL/authentication/production readiness settings; user-owned pnpm files remain untouched and excluded.

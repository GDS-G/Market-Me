# Existing-member role management and exact recovery

Release 1.33 implementation reference, reviewed local candidate. Final acceptance passes 2,647 tests/149 files, all static/frontend/native checks, 120 migrations/replay, synthetic desktop/mobile, production authentication/recovery and unsigned packaging. Its focused subset is 43 model, 39 live-database and 79 web contract/route/page tests. Exact-source cloud and final Google documentation acceptance remain pending before a released-source claim. The [original scope plan](WORKSPACE_MEMBER_ROLES_PLAN.md) remains the design boundary.

## Authority and product scope

A current workspace owner or administrator can change another current non-owner collaborator among admin, editor, approver, analyst and viewer. This matches the existing invitation administrator's ability to assign non-owner roles. It does not add the specification's future granular role taxonomy. No owner assignment/demotion/transfer, self-role change, membership creation/removal, organization grant, user/profile/identity edit, credential change or cross-workspace permission is available. Organization ownership alone is insufficient without qualifying workspace membership.

Each operation independently checks current membership. Existing `auth.ts` writer roles are owner/admin/editor and approval roles owner/admin/approver; analyst/viewer do not acquire either permission. Domain-specific checks still apply. UI role explanations summarize these boundaries, not promise unrestricted publishing or provider execution. Changes affect future authorization checks and do not retroactively undo completed work or work already admitted while its authority locks were held. Existing roles returned earlier to a browser are not continuing authority.

Building this feature does not authorize granting real people production access. Integration and browser acceptance use synthetic identities in named isolated databases; no live provider or production permission is changed.

## Source map and data types

Database files: `workspace-member-role-models.ts`, `workspace-member-role-repository.ts`, their tests, and frozen `0120_workspace_member_roles.sql`. Web files: `server/workspace-member-role-api.ts`, `app/api/v1/workspace-member-roles/route.ts`, `app/team/page.tsx`, `components/workspace-member-role-contract.ts`, `components/workspace-member-role-form.tsx`, and three focused test files. The editor reuses the presentational `workspace-management.module.css` styles; it does not reuse the workspace-name mutation contract. `database.ts` exports `getWorkspaceMemberRoleRepository()` and adds `workspaceMemberRoles` to its repository factory bundle.

`MANAGED_MEMBER_ROLES` is a frozen tuple `[admin, editor, approver, analyst, viewer]`; `ManagedMemberRole` is its union. The browser independently declares `MEMBER_ROLE_CHOICES` and a frozen `MEMBER_ROLE_DESCRIPTIONS` dictionary of plain-language capability explanations. Database runtime code is not imported into the client. The UI imports the member DTO as a type only.

`WORKSPACE_MEMBER_ROLE_LIMITS` is frozen: `reason=500` UTF-16 code units, `requestBytes=4096` UTF-8 bytes, `pageSize=50`, `maxPage=2000`. `WorkspaceMemberRoleRequest` is exactly `{workspaceId, targetUserId, requestId, expectedRevision, newRole, reason}`. `normalizeWorkspaceMemberRoleRequest` rejects non-ordinary prototypes, accessors, hidden/symbol and unknown fields before reading values. Its local `allowed` Set defines the six permitted fields. UUIDs trim/lowercase and require version 1–8/RFC variant; revisions are integers 1–2,147,483,647. Reasons reject C0/DEL before NFC/trim/whitespace collapse and must contain 1–500 UTF-16 units. The returned request is frozen, with that fixed field order for canonical JSON equality.

`WorkspaceMemberRoleReceipt` contains `{workspaceId, targetUserId, requestId, previousRole, newRole, revision, reason, createdAt}`. Both role fields exclude owner; `revision` is the resulting revision, not the submitted expected value; creation time is a server ISO timestamp. Internal `ReceiptRow` adds `createdBy` and `canonicalRequest`; `receipt()` explicitly removes them. A historical success never asserts today's role, continuing access or that the member still exists.

`ManagedWorkspaceMember` contains `{userId, displayName, role, revision, canChangeRole}`. Its role is the full existing six-role `WorkspaceRole`, including protected owner. `ManagedWorkspaceMemberPage` contains `{workspaceId, page, more, canManage, members}`. It omits email, credentials, organization grants and private receipt history. `canManage` comes from current owner/admin membership; `canChangeRole` additionally excludes self and owners. These display flags cannot authorize writes.

`WorkspaceMemberRoleError` has a cross-hot-reload `Symbol.for(@market-me/database/WorkspaceMemberRoleError/v1)` brand. Its closed codes are invalid_input, access_denied, not_found, protected_member, request_conflict and revision_conflict. `isWorkspaceMemberRoleError` requires an Error plus that brand, not a spoofable name/code. Transport errors are a separate class.

## Migration, history and revision behavior

Frozen migration `0120_workspace_member_roles.sql` has SHA-256 `3b993c63971ae6d74ee7c6ca1f30682c6859be13f9b1e2b72f63d7add4e6abe4`. It adds positive `workspace_membership.role_revision`, default 1, without rewriting existing roles/creation identity. Inserts must start at 1. A changed role advances the counter exactly once, including trusted administrative SQL outside this API; that SQL may leave the old value or specify the next value. Skipped counters, counters changed without a role change and overflow are rejected. Identity workspace/user/creation-time fields are immutable on update. Repeating the same role leaves its revision unchanged. A revoke/regrant cycle thus invalidates previously loaded revisions even when the final role string is unchanged.

The trigger is an integrity boundary, not protection against a trusted database administrator. Administrative SQL may still change owner roles or delete/recreate memberships; neither is exposed here. A deleted/recreated membership starts a new counter, so future membership-removal/rejoin product work must add an incarnation-aware stale-intent design. Operators must drain pending mutations before such out-of-band lifecycle changes or database restores; do not treat an old expected revision as proof of uninterrupted membership.

`workspace_member_role_receipt` has primary key `(workspace_id,request_id)`, target/actor app-user references with restricted deletion, before/after non-owner roles, resulting revision (>1), required bounded reason, canonical request (≤4096 UTF-8 bytes) and server `created_at`. The canonical JSON check enforces a closed object with matching IDs, role, string reason and numeric expected revision=result−1. SQL uses character count while application limits use UTF-16 units. The insert trigger requires current actor administration and exact target role/revision. Actor cannot equal target and before/after must differ.

Updates and individual receipt deletion are forbidden while the workspace remains. Only workspace erasure can cascade history. There is deliberately no foreign key to the membership row: future membership removal must not silently erase past permission changes. Referenced app-user deletion remains restricted while receipts exist. The `(workspace_id,target_user_id,created_at DESC)` index supports scoped history maintenance; no public history directory is exposed.

Audit event `workspace.member_role_changed` uses actor ID, workspace scope, subject type `workspace_member` and target user ID. Its minimized data is `{previousRole,newRole,revision,reason,sourceInterface:"team_role_editor"}`. Request and actor private canonical bytes are not included. Reason is intentionally retained in audit and private recovery; the form warns not to include secrets. Identity/membership counts, content, approvals and provider state are unchanged by the mutation.

## Transactions, locks and collections

`WorkspaceMemberRoleRepository` stores only its `sql` client, not actor or authority state. For mutation, validate/freeze/canonicalize input and normalize the separately supplied authenticated actor. In one transaction, select the actor and target memberships ordered by immutable `user_id` and lock both `FOR UPDATE`. Never lock the actor separately before the target: reciprocal A→B/B→A administrator demotions otherwise deadlock. The invocation-local `members` array is searched for current actor and target; no global membership cache exists.

After current actor owner/admin authorization, acquire the transaction advisory lock for `workspace-member-role:<workspaceId>:<requestId>` using `hashtextextended`. Hash collisions can serialize unrelated requests but do not merge exact database identities. Compare any prior row's actor and canonical bytes; exact replay returns the original receipt before today's target existence/owner/role/revision checks, without applying the old change again. Another actor or changed canonical input gets request_conflict. Replay still requires current actor authority.

For new work reject self/owner, absent or foreign target, no-op role, stale revision and exhausted counter. Update the existing membership role (the trigger derives next revision), then insert receipt and audit in the same transaction. Rollback cannot leave a partial grant. No workspace row lock is taken before membership locks; this respects existing workspace-name/invitation authority ordering. The current actor lock remains held until commit, so a concurrent revocation either precedes and denies the mutation or waits for its admitted transaction.

`getReceipt` locks the actor's current qualifying membership `FOR SHARE`, then reads only the exact workspace/request/original actor. It can wait behind an in-flight mutation's actor row lock. It does not acquire the mutation's advisory lock. An absent committed result or failed transport is not proof of failure. Target removal or later role changes do not rewrite an existing receipt; actor revocation prevents recovery until appropriate access is restored.

`listMembers` requires current membership held `FOR SHARE`. It reads `pageSize+1` rows ordered by membership creation time/user UUID, slices the first 50 and derives `more`. Offset is `(page−1)*50`; page range is 1–2000. Pagination is a loaded snapshot, not a stable cursor across concurrent membership lifecycle operations. No total count or unlimited member collection is loaded.

## API and Team UI

`POST /api/v1/workspace-member-roles` requires configured exact APP_BASE_URL Origin, no query string, authenticated actor, application/json, advertised and streamed body limits, fatal UTF-8 decoding and the closed request model. New success is 201; exact replay 200; both return `{data:receipt,meta:{replayed}}`. It sets no workspace-selection or authentication cookie. `GET` accepts exactly one workspaceId and requestId, no other or duplicate query values, authenticates and privately recovers `{data:receipt}` or 404 with an explicit may-still-finish warning.

All API responses are no-store. Statuses distinguish authentication 401, denied/protected member 403, absent target/result 404, request/revision conflicts 409, over-limit 413, unsupported media 415 and invalid input 422. Unknown errors return a sanitized uncertain-result 503; raw SQL, request contents, reasons and identifiers are not logged by the error handler. Stream readers use invocation-local `chunks` arrays, byte `length`, joined `bytes` and `offset`; oversized reads cancel, and reader locks always release.

The server Team page authenticates and resolves the active membership, then accepts only an optional unambiguous page query. Repository-derived fresh `canManage`, not the earlier active-workspace role, determines editor/invitation visibility. The member list labels itself a loaded snapshot, shows role revisions and uses bounded previous/next links. Invitations remain separate existing controls. No user/role/workspace query parameter can supply authority.

`WorkspaceMemberRoleForm` uses a hydration gate (`useSyncExternalStore`, inert server snapshot) so SSR never exposes an enabled editor before saved browser requests are inspected. Its remount key combines account/workspace with the page's member IDs/revisions/capabilities. The chooser contains only other currently manageable non-owners from this page. Review displays member name plus immutable UUID, loaded role/revision, proposed role and the effect description. Changing target/role/reason invalidates acknowledgement. Both disabled controls and the submit handler require acknowledgement, a valid target and a different role. Server checks remain decisive if these props are stale.

## Browser variables, storage and exact recovery

`MemberRoleScope` is userId/workspaceId. `MemberRoleAttempt` is `{version:1,userId,previousRole,request}`; previousRole is the loaded review snapshot, not caller authority. It is not submitted as a grant field. The browser requires returned previousRole to match that reviewed snapshot in addition to exact workspace/target/request/newRole/reason/resulting revision. `MEMBER_ROLE_BROWSER_LIMITS` mirrors reason 500/request 4096 and bounds saved recovery/responses to 8192 UTF-8 bytes. Strict Zod schemas reject unknown fields. `makeMemberRoleAttempt`/`restoreMemberRoleAttempt` validate, enforce scope/no-self/no-op and freeze both attempt/request.

Storage key: `market-me:workspace-member-role:v1:<userId>:<workspaceId>`. A single request per account/workspace covers all targets; changing members cannot overwrite an uncertain earlier grant. `persistMemberRoleAttempt` parses the entire attempt, compares any existing canonical serialization, writes and verifies exact readback before network dispatch. Failed/quota/silent/malformed storage prevents sending. `runMemberRoleAttempt` rechecks persistence, sends the same POST bytes or a read-only exact GET lookup, bounds and validates the response before success, and retains the attempt after every status/error/success. It never silently changes request identity.

Editor state: lazy `restored` holds exact raw saved serialization/validated attempt/read error; `attempt` freezes the sent intent; `storageError` blocks unsafe sends; `targetId`, `newRole`, `reason` hold unsent/restored values; `acknowledged` authorizes the reviewed initial change; `clearAcknowledged` separately acknowledges local recovery removal; `pending`, `error`, `result` describe in-flight/status/original receipt. Refs: `inFlight` is the immediate duplicate-action guard; `mounted` suppresses late component updates; `retained` identifies the exact local bytes safe to remove. `selected` and `editable` are derived from current page DTOs, never authority caches.

`clearMemberRoleAttempt` requires known raw serialization still matching the exact storage value, removes only that key and verifies absence. A malformed-but-readable value can be deliberately cleared; an unreadable or changed value requires reload first. The UI requires explicit acknowledgement, then performs a full team reload so stale revisions/authority are not reused. Clearing does not undo a server role change. Closing the tab can lose the local copy. Whole-workspace erasure or restoration to a pre-request backup can remove server evidence. Keep role revisions, receipts and audits together when restoring.

The server's `globalThis.marketMeDatabase` retains the repository bundle only in development; production factory calls do not retain it there. The new member-role repository has no independent global state. Restart development after changing this factory/class. No third-party dependency, secret, environment variable, external service, worker or provider capability is added.

## Rollout and verification boundaries

Back up and drain membership mutations before applying 0120, then deploy matching code and restart web processes. Readiness requires exactly 120/latest 0120. Preserve migration checksums and use only forward fixes after application. This increment cannot safely be downgraded by deleting receipts or decrementing revisions. A future member deletion/rejoin or owner-transfer design must revisit revision incarnations, audited lifecycle authority and pending recovery explicitly.

Integration tests allow only market_me_ci or market_me_qa_133_*; cleanup removes only fixture-owned organizations/users. Browser QA uses market_me_qa_133_roles_v1 with five synthetic members and no provider/source/publication records. The focused tests cover all 20 distinct non-owner transitions, low-role/organization-only denial, owner/self protection, exact concurrent replay, private history, stale edits, reciprocal-admin races, both revocation orderings, raw-SQL revision cycles, immutable history/erasure, pagination and downstream invitation/name-administration checks.

# Durable campaign activation recovery

Status: design implemented and verified in1.54 runtime `156729d3ebf909d450c095cc4ca927ea065a6a25`, now public on main. [Programmer reference](CAMPAIGN_ACTIVATION_RECOVERY.md) and [release evidence](RELEASES.md) record local/browser/native/feature-main cloud and Google preservation acceptance. The original reasoning below is retained; it is not a hosted-deployment or whole-product claim. No live provider account, marketing send or new user decision was required for this implementation and isolated verification.

## Problem and scope

The guided finalization result pins the published version and suppresses a second click only in component memory. The advanced editor posts activation without a version pin. Both currently create a fresh campaign instance for each accepted request. If the transaction commits but the response is lost, navigation or reload can lose the original reference and allow an unintended second run. Per-step/provider idempotency cannot deduplicate two different instance identities.

Provide one durable, exact activation request and immutable original receipt across both entry points. A repeated request must return the original run identity without another run, step set, start command or audit. Explicitly starting another run remains possible only through a fresh review and new intent after the prior result is resolved. This is request idempotency, not a global prohibition on multiple deliberate runs or an exactly-once guarantee for remote providers.

## Persistence and authority

Canonical intent is a bounded, fixed-order object: workspaceId, campaignId, requestId, expectedVersionId and expectedActorIncarnationId. All are exact normalized UUIDs; reject extra/missing/hidden/symbol/accessor properties before reading values. The actor comes only from the authenticated server context. Version and grant hints are stale-review fences, not authorization.

Use a new immutable receipt with workspace/request primary identity, original creator, reviewed grant and published version, resulting instance, initial status, accepted timestamp and canonical bytes. The run, exact step runs, durable start outbox, campaign status, receipt and minimized audit must commit in one transaction. Receipt identity must agree with the actual run's workspace, campaign, version and requester. Retain receipts through member removal/rejoin and later run progress. Do not retroactively manufacture receipts for old runs.

Lock order: current membership FOR SHARE; request-scoped transaction advisory lock; original receipt lookup; for fresh intent only, shared workspace execution admission fence; existing campaign/version/proof/route locks. Exact same-creator/canonical replay precedes checks of current execution state, version, schedules and grant incarnation because it is historical recovery, not a new run. Current writer authority remains required for POST. A current member may read only their own original receipt; no foreign-creator or cross-tenant discovery. New requests require current owner/admin/editor membership and exact active grant incarnation. Test revocation/rejoin, real lock waits, exact concurrent requests and rollback of every write if audit fails.

Reuse the established activation proof, approval, rights, route, schedule and outbox code inside the same transaction. Do not duplicate or relax those gates. Keep read-only original recovery available when execution is paused or a published version/preview has changed. Do not start, resume, approve or dispatch a workflow from a GET. A 404 means no committed receipt was observed; an earlier transaction may still finish.

## Web behavior

Replace both direct activation controls with the same scoped review/recovery surface. Display the exact published version and consequences; unsaved drafts are excluded. A fresh preview and explicit acknowledgement precede intent creation. An expected-version link from the protected finalization result must not silently switch to a different current version.

Before POST, persist the exact original attempt in sessionStorage under user/workspace/campaign scope. Storage failure sends nothing. Store only bounded identifiers and correlation fields, never credentials or authoritative campaign/proof data. Restore validates schema and all scopes before permitting read-only recovery; a reload or timeout never automatically POSTs, generates a replacement key or assumes failure. Current server authorization and grant checks remain authoritative. Browser storage is tab-local, may be copied with a duplicated tab and can be cleared by the user; document these limits. Exact same-key requests from copied tabs still resolve to one run.

The synchronous in-flight ref must fence duplicate click handlers before React updates. Use one abortable bounded transport operation with fatal UTF-8, response-size and timeout limits, no redirects, no-store and same-origin credentials. Validate every receipt field against retained intent and status/replay envelope. An unknown response retains intent and offers GET-only lookup. Original receipt and current live run status are separate observations. New deliberate runs require explicit completion/acknowledgement and a new fresh review, not a generic retry button.

Implementation review identified an important refinement: GET 404 alone cannot safely unlock a new request, and a rejected/stale request could otherwise trap the user indefinitely. Add an explicit close-original-request operation, serialized on the same durable request lock. If activation already committed, closing returns its original receipt and does not cancel the run. Otherwise a durable immutable closure prevents later use of that key. Closing requires current member access and exact creator/canonical correlation for existing history; it never starts work or waives writer authority. It is separate from read-only lookup and needs an explicit consequence acknowledgement. Only a confirmed acceptance or confirmed closure permits deliberate new intent. A lost close response retains the same key for GET recovery. Migration 0130 was already applied to isolated CI; implement this refinement in additive 0131, never by modifying 0130.

API POST requires configured same-origin, no query, strict bounded JSON with duplicate-key rejection and session authority. Missing new intent fields fail closed; old clients cannot silently obtain a new request identity. GET supports tightly bounded preview or exact original-request lookup. Responses are fixed/private/no-store/Vary Cookie/nosniff, with no credentials, arbitrary exception details or SQL in user-visible errors/logs. Keep publishing separate and preserve its current version-pinned idempotency contract.

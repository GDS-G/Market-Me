## Product boundary and integration

Team presents a nonmutating impact review for one other non-owner member, then a reason and separate explicit acknowledgement before removal. Self and all owner grants are protected; owner transfer, last-owner policy, organization membership changes, account deletion, administrator-wide session management, bulk offboarding and automatic responsibility reassignment are excluded. The member's account, sign-in sessions, other workspaces, provider/companion credentials, original attribution, conversation read state and work records remain. Subsequent independently authorized requests cannot use the revoked workspace grant. Already-admitted work can finish; externally delivered content is not recalled.

The original schema has 63 membership FKs across 38 tables: 56 RESTRICT, four NO ACTION and three CASCADE. Removing a physical membership would either fail against provenance or erase read/presence/mention state. The new design retains the original physical relation and every old FK. All current-authority reads explicitly select the active-grant view instead; historical identity is not mistaken for permission. This is normal application authorization, not a SQL sandbox against the trusted database owner.

## Permanent identity and current grant schema

Migration 0125 adds `workspace_membership.incarnation_id` (fresh UUID, not nullable, unique) and `revoked_at` (nullable timestamp), with a partial active user/workspace index. It preserves workspace_id, user_id, role, created_at, role_revision and all dependent foreign keys. `active_workspace_membership` is an invoker-security view selecting workspace_id/user_id/role/created_at/role_revision/incarnation_id only where revoked_at is null, with LOCAL CHECK OPTION. Its simple projection supports underlying row locks and role updates. Neither grant UUID nor role revision is a bearer credential.

The existing `guard_workspace_member_role_revision` trigger function is forward-replaced; a DELETE trigger additionally retains identity while both parents exist. Insert requires revision one and an active initial grant. workspace_id/user_id/created_at are immutable. Actual role change, revocation and regrant each advance role_revision exactly one; no-op writes preserve it. The counter cannot reset, skip or overflow 2,147,483,647. An inactive row cannot change role or its original revoked timestamp. Regrant requires revoked_at to become null and a new incarnation UUID; other transitions cannot change incarnation. Parent workspace/account cascades remain possible subject to existing history constraints. These guards do not make arbitrary trusted SQL an authorized product action.

Migration 0125 also forward-updates exactly nine membership-authority references in six existing SQL guards: source-preparation binding, smart-source setup receipt, preparation-preset history, workspace management receipt, member-role receipt and AI-policy save receipt. It checks each expected replacement count and preserves the rest of each function body. Original migrations 0116–0121 are not rewritten. Migration tests compare original/updated function bodies exactly, preserve legacy columns/identities, and exercise retained RESTRICT/CASCADE records and parent cascades in rollback-only schemas.

Existing role-change request bytes remain compatible: workspaceId/targetUserId/requestId/expectedRevision/newRole/reason. The monotonic counter makes stale uncommitted role edits conflict after remove/rejoin. Old role receipts retain their original facts; no invented incarnation is retroactively attached. Exact historical role replay returns the old receipt without applying its role to a new grant.

Migration 0126 introduces `workspace_member_removal_receipt`:

| Field | Intent and retention |
| --- | --- |
| workspace_id, request_id | Composite intent identity; workspace deletion may cascade the receipt. |
| target_user_id, created_by | Retained app-user FKs with RESTRICT; actor must differ from target. |
| expected_incarnation_id | Grant that was removed, not necessarily the person's later current grant. |
| previous_role, revision | Removed non-owner role and post-revocation monotonic revision, greater than one. |
| reason | Bounded nonempty reviewed reason retained in receipt and audit. |
| impact_fingerprint | Lowercase 64-hex SHA256 preview identity fence, not a secret signature. |
| impact | Exact eleven-key JSON object of canonical nonnegative decimal strings, at most 19 digits each. |
| revoked_at | Original exact database timestamp. SQL INSERT SELECT avoids rounding through JavaScript Date. |
| canonical_request | At most 4,096 UTF-8 bytes of fixed-order normalized seven-field request JSON. |

SQL CHECKs require every canonical member's actual JSON type/value, reject extra keys, and bind expectedRevision to stored revision minus one. `valid_workspace_member_removal_impact` rejects nonobjects, missing/extra keys, numeric rather than string counts, negatives, leading zeros and overlong counts. The immutable receipt guard requires a current active administrator and the exact retained target incarnation/role/revision/revoked timestamp; pending incoming/issued invitation counts must be zero. Updates/direct deletes fail while the workspace exists. These checks supplement server authority and computation; they do not authenticate caller-supplied SQL or prove a hash was secret.

Migrations 0125/0126 have been applied only to isolated market_me_ci and the new synthetic market_me_qa_152_members_v1. Their checksums are fixed; any further schema correction must be a forward migration. The prior 1.51 QA fixture remains at 124 migrations. Real/default development data has not been migrated for acceptance.

## DTOs, constants and collections

Frozen `WORKSPACE_MEMBER_LIFECYCLE_LIMITS` defines reason=500 UTF-16 code units, requestBytes=4096 and revision=2147483647. `WorkspaceMemberRemovalRequest` has exactly, in order: workspaceId, targetUserId, requestId, expectedIncarnationId, expectedRevision, impactFingerprint, reason. UUIDs are canonical hyphenated version 1–8/standard variant, lowercased without trimming. Revisions must leave room for one increment. The fingerprint is 64 lowercase hex characters. Reasons are NFC-normalized, trimmed, internal whitespace collapsed, and reject Unicode control/format/lone-surrogate characters. Legitimate Unicode/emoji remain allowed. Normalization inspects all descriptors before value reads and rejects accessors, hidden/symbol/unknown fields and nonordinary objects, then freezes the exact request. No actor, role, restore flag or client authority hint is accepted.

`WorkspaceMemberGrant` contains userId/displayName/role/incarnationId/revision. `WorkspaceMemberRemovalPreview` contains workspaceId,target,observedAt,impact,impactFingerprint,blocked. `WorkspaceMemberRemovalReceipt` extends the exact request with previousRole,post-change revision,revokedAt and impact. It is historical and never asserts that a subsequent invitation has not regranted access. Public timestamps use ISO UTC millisecond precision; internal receipt equality retains exact PostgreSQL timestamps. Private MemberRow/ReceiptRow types can hold revokedAt,createdBy,canonicalRequest, but the public receipt mapper explicitly strips internal provenance/storage fields.

Frozen ordered `WORKSPACE_MEMBER_IMPACT_KEYS` defines these exact counts, all strings rather than rounded JavaScript numbers:

| Key | Included records; no implicit mutation |
| --- | --- |
| assignedConversations | Conversations assigned to target, excluding resolved/archived. |
| enabledRoutingRules | Enabled inbox rules targeting this member. |
| openConversationReviews | Open reviews whose requested reviewer is target. |
| pendingCampaignApprovals | Pending approvals assigned to target. |
| pendingIncomingInvitations | Unexpired pending exact-normalized-email invitations for target. |
| pendingIssuedInvitations | Unexpired pending invitations issued by target. |
| enabledSourceBindings | Enabled source bindings whose writer is target. |
| queuedSourceCommands | Target-writer source commands pending, processing or failed. |
| preparedAiIntents | Target-prepared, unexpired prepared intents; not a claim that execution has never happened. |
| activeCampaignRuns | Target-requested campaigns awaiting approval, scheduled, active or paused. |
| ownedDestinations | Target-owned destinations that are not archived. |

Only nonzero pending invitation counts block removal outright; other counts are disclosed retained responsibilities. The application does not invent an assignee or cancel work. All eleven counts are computed in one statement-time snapshot and rechecked before a new removal. `workspaceMemberImpactFingerprint` hashes a fixed JSON array: version tag, normalized workspace UUID, current actor grant UUID, target UUID, target grant UUID, target revision and the ordered [key,count] pairs. Labels and observedAt are not identity. Another actor or a removed/rejoined actor cannot use the old preview. Count/grant changes require fresh review. This does not lock all work tables or promise that already-admitted operations cannot finish after the snapshot.

The branded `WorkspaceMemberLifecycleError` uses Symbol.for plus an Error check. Codes are invalid_input,access_denied,not_found,protected_member,revision_conflict,request_conflict,impact_conflict,unresolved_dependencies. The brand handles module reloads, not malicious in-process code.

## Transaction ordering, rejoin and exact recovery

`lockWorkspaceMemberGrant` takes a transaction-scoped advisory key derived from JSON [workspace-member-grant-v1,workspace UUID,normalized email] before invitation/member row locks. It coordinates one potential grant, not all workspace activity. Normalized email is internal and never enters the public preview, receipt or removal audit. Hash collisions can serialize unrelated operations but do not grant authority.

Removal first performs preliminary current-admin admission to minimize private target-email lookup; it then takes the grant key and locks retained actor/target membership rows in sorted user-ID order FOR UPDATE. Only the actor's active owner/admin row is authority. It next takes the exact [workspace-member-removal-v1,workspace,request] advisory key. The original receipt is checked before target current-state checks: same actor and exact canonical bytes return historical success, never a second revoke; changed bytes/actor conflict. New intents require a current nonself/nonowner target with exact incarnation/revision, the current actor-bound impact fingerprint and no pending invitations. UPDATE sets revoked_at=clock_timestamp; the guard advances revision. Receipt INSERT SELECT and minimized audit share the same transaction and roll back together on failure.

The audit is `workspace.member_access_removed`, subject_type workspace_member, subject_id target UUID, actor_user_id current administrator. Data contains requestId,incarnationId,revision,previousRole,reason,impact,sourceInterface=team_member_removal only. It contains no email, credential, content body or list of private work objects. `getReceipt` requires a current active owner/admin FOR SHARE and matches exact workspace/request/original creator; another administrator cannot browse someone else's request history. An absent receipt is not proof an in-flight operation failed.

Invitation creation and revocation now take the same workspace/email grant key before the actor membership lock. Removal also locks the target membership, so a target issuing invitations is ordered with offboarding. An old unexpired incoming or issued grant must be explicitly accepted/revoked/expired before removal. A newly authorized invitation created after completed removal is a separate deliberate grant, not an automatic restoration.

OIDC uses a same-normalized-email `oidc-account-provision-v1` advisory key for first provisioning. Existing app_user reads use FOR KEY SHARE rather than taking a user UPDATE lock before membership locks; receipt foreign keys also require KEY SHARE. This avoids the tested role-receipt/OIDC membership lock inversion. Existing linked identity rows remain locked and authoritative for account identity; a provider's changed claimed email/name does not rewrite the linked Market Me account.

Invitation acceptance discovers at most 100 unexpired pending workspace candidates without locks, deduplicates/sorts scope UUIDs and acquires all corresponding grant keys before invitation/member rows. Its final query only processes those scopes, ordered by workspace/invitation UUID. New other-workspace candidates are left for later sign-in. It rechecks pending status and expiry against clock_timestamp AFTER invitation/member lock waits. Existing active membership preserves role/incarnation/revision. Explicit acceptance for a revoked membership updates role from the invitation, clears revoked_at, supplies a fresh UUID and advances the existing revision; created_at remains original. Without a new valid invitation, linked sign-in may authenticate the account but cannot restore removed workspace authority. Organization membership insertion remains separate and does not become workspace permission.

Invitation-acceptance audit retains role and adds membershipGranted plus incarnationId/revision only when a grant is actually created/regranted. No-op active-member acceptance does not fabricate a grant change. Transaction-local candidates/scopes/invitations/granted/accepted values are not global state. Tests cover concurrent first linking and the real role-lock/user-FK inversion.

## HTTP and browser boundary

POST `/api/v1/workspace-member-removals` requires exact configured Origin, no query, current independently authenticated user, application/json, advertised/streamed body at most 4096 UTF-8 bytes, fatal decoding, valid JSON and duplicate-key rejection including escaped aliases. The database normalizer remains independent. Success is 201 with `{data:receipt,meta:{replayed:false}}`; exact replay is 200 with true. GET accepts exactly workspaceId plus either targetUserId for a read-only current preview or requestId for original-actor recovery, never both/duplicates/extra fields. It never creates a removal.

Every response is private,no-store, Vary Cookie and nosniff, without cookie mutation. Error text is a fixed minimized dictionary; raw exceptions/request bodies/SQL details are not logged or echoed. Codes map to 401 anonymous,403 origin/authority/protected,404 missing,409 changed grant/impact/request/unresolved invitations,413 size,415 media,422 shape and503 unavailable. Public UUIDs may appear in ordinary access logs; reason and impact are body data, not URL query fields.

The independent browser Zod module has no database runtime import. Frozen limits are reason500,request4096,response16384,timeout15000,revision2147483647. Frozen MEMBER_REMOVAL_IMPACT_LABELS maps every count key to truthful operator text. Strict preview validation checks exact fields, bounded names, nonowner role, count strings, UUIDs, revision, ISO time, hash and blocker/count coherence, then freezes target/impact/preview. `makeMemberRemovalAttempt` binds user/workspace, exact preview, generated request UUID and normalized reason; it refuses blocked/self/exhausted grants and freezes the local attempt/request. Server recomputation remains authoritative.

`runMemberRemovalAttempt` reconstructs/compares exact intent before sending. It issues one POST or an explicit GET only, using same-origin credentials,no-store,redirect:error and cancellation checks before send/after bounded response parsing. Receipt validation binds every request field, previousRole, next revision and all reviewed counts. It rejects unsupported response fields/statuses and uses fixed local error guidance. No automatic retries, localStorage, sessionStorage, recovery cookie or unknown-key lookup are introduced.

The panel is keyed by userId/workspaceId, not a stale role hint. Local preview/reason/confirmed represent one reviewed selection; attempt/result retain original intent and historical outcome; pending/error are UI state. retained is a synchronous ref preventing double submission before React rerenders. mounted and the form-local gate controller/timer suppress late updates; timeout cancels at 15 seconds, old completion cannot unlock a newer operation, unmount cancels. Router refresh updates the team without discarding a same-scope original request. Reload/paging/leaving loses the local reference; server receipt retention is separate and plainly disclosed.

Review only loads GET and focuses a heading via a local DOM ref. Cancel returns focus to the originating button. Submit requires current reviewed preview, nonempty reason and explicit checkbox. Once sent, selection stays locked and Check original removal result uses GET only. Abort, timeout or 404 does not prove rollback. The confirmed view explicitly labels an original historical revocation, not current absence after a possible later rejoin. Scoped CSS wraps identifiers, uses 44px minimum controls and 3px keyboard focus; reason guidance warns against sensitive details.

## Resolving invitation blockers

The legacy latest-200 mixed history cannot reliably expose an older pending invitation. Team therefore accepts an optional single canonical invitationMember UUID alongside its existing bounded member page. Only current administrators may use the filter. `listPendingInvitations` locks actor/target retained rows in the same sorted order, requires the actor still active/admin, and selects at most 200 currently unexpired pending invitations whose email matches target or invited_by equals target. Target historical identity is permitted so a post-removal refresh of the filtered page does not erase the original result. No inactive target becomes an authorized actor.

This is a resolution queue: only related pending grants are shown, ordered by created_at/id. Revoking a visible grant exposes the next on refresh; unrelated invitations never need to be cancelled to uncover a blocker. The filtered view suppresses invitation creation and labels the member ID/issuer. Empty filtered state directs a fresh removal review. Unfiltered history remains unchanged. Query UUID is a filter, not authority.

Existing selected invitation DELETE now validates Origin/UUID/no query before fresh workspace authority, then the core transaction rechecks current actor authority after its grant key. Responses/errors use the private fixed-message boundary. TeamInvitations is keyed by user/workspace/filter, uses a synchronous inFlight ref and mounted guard, and sends explicit selected DELETE with a 15-second timeout, redirect:error and bounded response checking. It verifies returned id/workspace/status before success. Network uncertainty tells the operator to reload instead of assuming failure; no automatic retry or bulk revocation occurs. These changes do not send email or install identity-provider credentials.

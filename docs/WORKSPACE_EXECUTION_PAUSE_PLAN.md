# Workspace-wide outbound execution hold

Status: accepted 1.53 implementation, reviewed runtime `1dbb15a723ce9a484d15ef192ede71f0429a3126` public on main. Full local and independent feature/main gates each pass 4,643 tests/226 files and 44 quality cases; native/unsigned packaging, actual desktop/mobile/production checks, 143/147-table preservation and final Google readback pass separately. [Implemented programmer contracts](WORKSPACE_EXECUTION_PAUSE.md) supersede the design questions below; [release evidence](RELEASES.md) records exact runs and limits. Separate AI/worker controls remain; this is not a deployment-wide operator kill switch or whole-product completion.

## Requirement and scope

Specification 11 requires emergency pause, action history, budget ceilings and human takeover; specification 18 calls for stopping outbound execution without deleting campaign state. The next implementation should give a current workspace owner/administrator one visible, durable hold covering new marketing publication admission, claimed companion execution and billable AI text attempts in that workspace. It must not grant an administrator authority over another workspace or tenant. Deployment-wide operator controls and network isolation remain distinct operational requirements.

Use the existing application, current membership and synthetic test infrastructure; no live provider credential, payment, real account change or hosted deployment is needed to implement and verify this boundary. Do not activate a real workspace hold during development. Use isolated fixtures and fake transports for race tests.

A pause blocks new admissions. It cannot recall already delivered content, prove that an uncertain request was not accepted, stop an already-open browser action, or guarantee cancellation of an external HTTP call admitted before the hold committed. The UI must state those limits. Success/ambiguity reconciliation and actual-cost settlement must continue while paused; freezing settlement could hide a billable result or lead to a duplicate retry. Existing accounts, connections, secrets, approvals, drafts, campaigns, runs, schedules and exact provider outcomes must remain unchanged.

Resuming removes only this hold. It must not enable stopped AI execution, reactivate a revoked connector/worker, restore a removed member, revive expired schedules, waive approval/rights/budgets, resend ambiguous publications or mass-resume individually paused campaigns. Every existing policy still applies. Separate operator review is necessary for work that reached a visible recovery state while the hold was active.

## Existing execution surfaces to integrate

- `PublishingRepository.beginPublicationAction` and `retryPublicationAction` share `admitPublication`; both create a new remote-write admission and must be fenced. Exact historical read/recovery and finish/reconciliation paths must remain usable. Admission currently locks instance, version, steps, runs, approvals, connection and exact draft/asset/rights evidence before dispatch.
- `CampaignRepository.assertStepExecutionAuthorized` is the early activity gate, not the last-mile transaction. It should explain a hold before unnecessary provider preflight while the durable publication boundary remains authoritative. Activation/resume must not silently bypass the hold. Existing individual campaign cancellation and inspection must remain available.
- `CompanionRepository.claimNextJob` currently claims queued or lease-expired work from an active worker; a server hold must prevent new claims without deleting/revoking workers or queued history. Existing claim completion must retain truthful outcomes. Review queue creation and campaign-router fallback so a paused official route cannot silently switch to companion or manual delivery.
- `AiRepository.claimWorkspaceTextInvocationAttempt` is the one-billable-attempt admission before credential decryption/provider invocation. A workspace hold must complement, not replace, the current deployment enable flag, short-lived AI execution grant, health, circuit, privacy, quote and reservation checks. `completeWorkspaceTextInvocationAttempt` must retain actual outcome/cost handling for already-admitted attempts.
- `createCampaignActivities`, `CampaignExecutionRouter` and the Temporal scheduled/legacy workflows need an explicit non-dispatch hold result/recovery contract. A generic thrown database error that exhausts activity retries and marks a campaign failed is not an adequate pause experience. A new result type must not let an old manual-completion signal claim a held, undispatched action succeeded.

Diagnostic reads, authentication/OAuth maintenance, inbound collection, retained historical recovery and local drafting are not marketing dispatch. Inventory any remaining outbound mutation paths before claiming universal coverage; do not treat this list as proof that all connector operations are fenced.

## Persistence and authority design requirements

Implemented contract foundation: `workspace-execution-control-models.ts` defines frozen WORKSPACE_EXECUTION_STATES=[open,paused] and WORKSPACE_EXECUTION_CONTROL_LIMITS={reason:500 UTF-16 units,requestBytes:4096,revision:2147483647}. Open means only the additional hold is absent, not that work is approved/due. The exact fixed-order request is workspaceId,requestId,expectedActorIncarnationId,expectedRevision,state,reason. Identifiers require hyphenated UUIDv1–8/standard variant, lowercased without whitespace trimming; expected revision must leave one increment. A descriptor preflight rejects nonordinary objects, getters, hidden/symbol/extra/missing fields before value reads. Reasons reject Unicode control/format/lone surrogates, NFC-normalize, trim and collapse spaces; final canonical UTF-8 size is bounded and the result frozen.

WorkspaceExecutionControlReceipt extends that exact intent with previousState, post-change revision and changedAt; it is historical, not a current-state assertion. WorkspaceExecutionControlSnapshot has workspaceId,state,revision,changedAt and a discriminated canManage union: only true carries the current actorIncarnationId and reason. WorkspaceExecutionControlError uses a versioned Symbol.for brand plus Error validation; codes are invalid_input,access_denied,not_found,revision_conflict,request_conflict,state_conflict,execution_paused,control_unavailable. Module-level values are immutable constants/error identity only; descriptors,allowed,keys,raw,reason and request are call-local. The expected actor incarnation fences stale review after removal/rejoin but does not identify/authenticate the caller. The 58 pure tests cover these boundaries without database mutation or external dispatch.

### Implemented persistence and lock protocol

Migration 0127 is applied only to the isolated `market_me_ci` database and is now checksum-fixed: SHA-256 `defe01f7065aca857292f9274dfd02856c915ea2ecdbfa6aa6f59763e429cbc2`. `workspace_execution_control` retains one row per workspace, initialized at open/revision 1 with no actor or reason, backfilled with original workspace creation time and automatically created by an AFTER INSERT workspace trigger. Later transitions require an actual state change, exactly one revision, nonempty reason and a current owner/admin incarnation. Direct state deletion is rejected; parent workspace cascades remain supported.

`workspace_execution_control_receipt` has workspace/request primary identity and unique workspace/post-transition revision. It stores creator, expected actor incarnation/revision, previous/current state, reason, exact database timestamp and bounded typed canonical JSON. The insertion guard binds all evidence to the current state transition; receipts cannot be updated or directly deleted. No JavaScript Date round-trip occurs when persisting exact PostgreSQL timestamps: receipt insertion SELECTs the control timestamp within SQL. Public projections use ISO milliseconds only for display/history lookup.

`WorkspaceExecutionControlRepository` reads current membership FOR SHARE, then the control row. Mutation takes the membership lock, a transaction advisory lock keyed by JSON `[workspace-execution-control-v1,workspaceId,requestId]`, and a control FOR UPDATE lock. Exact same-actor/canonical-byte replay returns original history before current-revision checks; it never reapplies that transition. Fresh intent must match current actor incarnation and control revision. State, receipt and minimized `workspace.execution_paused`/`workspace.execution_reopened` audit commit together. Current nonadministrators receive no reason/incarnation; exact receipt recovery remains current-administrator and original-creator private. Removal/rejoin may restore historical lookup but never authorizes a stale new mutation.

Migration 0128 is also applied only to CI and checksum-fixed: SHA-256 `de0448fe04b5cb55abb969684702b24d03408e761c1319c84b5456d183898f81`. New publishing and retry admissions, AI text claims and companion claims take a shared workspace-control row lock before other execution-resource locks. Read-only target/member scope validation may precede this lock, but does not acquire competing resource locks. Pause/resume needs the conflicting exclusive control lock. No external provider call runs inside either transaction; already committed admissions may finish after a later pause.

`assert_workspace_execution_admission` additionally fences direct/older SQL writers: publication transitions to dispatching, AI transitions to claimed, and companion claims/reclaims including token, lease or attempt changes. SQLSTATE MM001 means paused and MM002 means unavailable; both fail closed. Completion transitions, read-only reconciliation and queued job storage are intentionally outside these triggers. `lockWorkspaceExecutionAdmission` maps current state to fixed branded application errors. Companion polling returns no job for a pause, retains queued/expired claims and rechecks worker identity/status FOR SHARE after the workspace lock; reopening the workspace never reactivates a paused worker.

Evidence: 16 rollback-only migration tests; 15 repository tests including current roles, tenant/privacy separation, six concurrent exact retries, competing revisions, stale resume replay, revoked/rejoined actor, actual revocation lock waits, atomic audit failure and missing-state failure; 12 admission/guard tests including all three SQL surfaces and observed waits for pause/admission commit and rollback in both orders. Real publication tests verify blocked begin/retry, immutable earlier evidence and completion/recovery after pause; companion tests verify queue/expired-claim preservation and completion of an earlier claim; the existing comprehensive AI fixture verifies no claim writes while held and actual-cost settlement for an earlier claim while held. These are synthetic database tests, not live provider or browser acceptance.

Keep one durable workspace-scoped state with a monotonic revision and truthful default/backfill policy. Decide whether its always-present row is created through workspace creation or a database trigger; missing/inconsistent state must fail closed for new outbound admissions after rollout. Do not infer authority from a client `canManage` flag or organization ownership. Read current active workspace membership under the appropriate lock at mutation/recovery time.

Pause/resume needs a bounded reason, explicit intended state, exact request UUID and expected state revision. A stale resume must never undo a later pause. Commit state transition, immutable original receipt and minimized audit together. The same actor/exact normalized bytes can recover the original historical result, but replay cannot reapply a prior resume after a newer hold. Preserve original receipts across member removal/rejoin and label history separately from current state.

Normalize requests independently at database and HTTP boundaries; reject ambiguous fields/getters/duplicate JSON, excessive UTF-8, mismatched workspace and unsafe reason controls. Use fixed public errors, private/no-store responses and creator-private exact recovery. Browser state is not authority, and unknown/aborted responses do not prove the original transition failed. Do not automatically retry or replace pending intent.

The admission/hold lock protocol needs a documented total ordering, not a UI-only or process-local Boolean. Admissions may share a workspace fence; pause/resume must take the conflicting lock and read current state after waits. Inspect existing member, workspace, instance, provider and invocation locks before choosing the order. Test both commit/rollback sides and actual blocked statements. Avoid an exclusive workspace fence held while waiting on a member lock already owned by an admission that is waiting for that fence.

Consider forward SQL admission guards for new `dispatching` publication transitions, claimed AI attempt insertion and companion claims, so old writers fail closed after the migration. Receipt integrity and state-revision guards must preserve normal parent cascades without permitting direct audit-history deletion. These are trusted-application consistency boundaries, not protection from arbitrary database-owner SQL. Applied migrations must remain checksum-fixed. A coordinated code/worker/schema rollout is required; do not accept a mixture of old writers and an unenforced new button.

## UI and operational acceptance

Place the control in an existing administration surface with an unmistakable current-state summary and link from appropriate execution screens. Current members may see a minimized state; only current owner/admin may change it. Make pausing readily discoverable and resuming deliberate, with reason, current revision and consequence review. State that already-admitted work may finish and that resume does not restart/approve other work. Keyboard focus, narrow layouts, loading, conflict, uncertainty and exact recovery are part of acceptance.

Automated acceptance must prove role/tenant separation, stale resume, exact replay, atomic audit rollback, upgrade/default/new-workspace state, actor revocation, pause versus each admission in both lock orders, no hidden fallback, existing-result recovery and settlement while held, no duplicate sends, interrupted worker restart and expired scheduling behavior. Temporal history compatibility requires an explicit patch/version decision and real history replay if workflow command behavior changes.

Use an isolated multi-workspace fixture to compare all relevant table fingerprints and transport invocation counts before/after pause, blocked admission, resume and historical lookup. Test real browser desktop/mobile/production interaction without dispatching to any live provider. Update the existing Google development parent and architecture/domain/build/security/release children with implemented contracts, variables, schema, locks, boundaries and exact evidence. A passing unit suite or visible hold button alone is not this feature's completion.
